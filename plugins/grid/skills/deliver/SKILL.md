# Deliver

Delivery writes down what exists. It does not decide that the work is good and it does not close the task.

On a task with a ship approve step it runs twice: first `## Before the gate`, so the person approves with the whole Outcome in front of them, then the full Steps after `ship approved`. A task without a ship approve step is delivered once, with the Steps, as before.

The task folder is `<projects folder>/<project>/tasks/T-NN-slug/`. The projects folder is `GRID_PROJECTS`, else `$GRID_HOME/projects` (`GRID_HOME` is the Grid data folder `~/.grid/<name>`, never the workspace folder; if both are empty, Grid is not set up for this folder: say so and write nothing). If the person does not say which task, take the only open one, else ask. Never search the disk for it. Every path below is under that absolute task folder; nothing is written relative to the working directory, which is the project's repo.

## First check

Read `task.md`. If `status: closed`, say the task is closed and stop: this skill never reopens a task and never changes a closed task's files. If the work is not finished (the current `step` is not the last in `workflow`, or a brief for it is `briefed`, `running` or `blocked`), say what is missing and stop. The one exception is `## Before the gate` below: it runs at a ship approve step, which later steps may follow, once the build's briefs are `done` and reviewed.

## Before the gate

A ship approve step is an `approve` step after the build (not the plan's approve step). The execute skill calls this part each time it raises that gate, once the review of the finished work is `ACCEPTED` and before it sets `status: waiting`; again after a change asked at the gate that led to more work, so the Outcome always describes the latest work. The work counts as finished here when the build's briefs are `done` and the review accepted them.

1. Run Steps 1 to 4 below as written (collect, artifacts/, the `outcome:` line and the `## Outcome` blocks, a reviewer's word), with two differences in step 3: leave `next` to the execute skill, which names who approves, and write the body line as `- <D Mon> · <step> · outcome written for the gate`.
2. Refresh `views/result.html` through the views skill.
3. Append one history.md line `- <time> · outcome written · <N> briefs done` (N = the briefs in `subagents/` with an Outcome). It is a marker, never an approval line.
4. If proposals with `status: proposed` already wait in `brain-proposals/`, start `grid-curator` on them now (no person is asked). Stop there: no `delivered` history line, no landing, no new brain proposals, no `views/plan.html` refresh and no `status` change. Those wait for `ship approved`.

When the work ran on an environment and the plan items it covers are not yet recorded as deployed there, record them before step 1 with `node "$CLAUDE_PLUGIN_ROOT/skills/execute/scripts/item-record.mjs" <task folder> deployed <N[,N]> --by owner --env <environment id>` (the id from the project's `environments.json`; the script refuses an unknown one and writes the history line itself). Skip it when nothing was deployed.

## Steps

1. **Collect.** Read `intent.md`, the briefs in `subagents/` that are `done` (Outcome and Verdict) and `plan.md`. The deliverables are the files the briefs name.
2. **artifacts/.** Every deliverable the person receives (a document, a mock, a report, a build log, a link list) is in `artifacts/`. Copy a file that lives elsewhere in the workspace there with Bash `cp`; never move it, and never copy a file from outside `$GRID_HOME`, the projects folder or the project the task names. Code changes stay in the project; point to them by path in the outcome. Do not rewrite or reformat a deliverable.
3. **Outcome in task.md.** Set the frontmatter `outcome:` to one line: what was delivered, in the person's terms, with the main path (for example `Release note for tag search written: artifacts/release-note.md`). Set `summary` if the work changed what the task is. Set `next` (on a task with no ship approve step, for example "Alex reads the result and closes the task"; after a last-step `ship approved` leave `next` as it is, Grid closes the task). Set `updated` (the output of `date +%Y-%m-%dT%H:%M`, run just before this edit, never a guess). Add a body line `- <D Mon> · <step> · delivered: <what>`. Edit with the Edit tool, never a shell redirect.
   Then write the result under a `## Outcome` heading at the end of task.md's body; on a task delivered before, replace that section whole. After `ship approved`, an Outcome written before the gate stays as it is unless something changed since (the landing commit, a measure, a file in artifacts/): then rewrite only the blocks that changed. The body's log lines stay above it: a later body line goes before `## Outcome`, never after it. Grid's Result tab shows these blocks in this order, so write them for the person, not for a coder:
   - `### Summary`, always: two to four plain sentences on what was done and why it matters, that someone who does not code can follow.
   - `### Before and after`, when the work changed something you can count: one line per measure, `<measure>: <before> -> <after> <unit>`, a number on each side of the arrow and the same unit on every line (for example `Lost: 2 -> 0 syncs` and `Kept: 38 -> 40 syncs`).
   - `### Not in it`, only when the task needs it: one bullet for each thing left out on purpose, and why.
   - `### After the deploy`, only when a deploy is part of the plan: at most two lines. Write `Waits: <text>` now, saying what to watch or do once it is live; add `Measured: <text>` below it once that has been measured, when the task is closed (for example `Waits: Syncs dropped per day in the first week, against 2 of 40 before.` and later `Measured: 0 of 40 syncs dropped in the first week.`).
   Leave out a block that has nothing to say, so a simple task stays lean: not every task delivers code or files. The Result tab's checks come from the plan's `verify` lines; keep those lean on a simple task too. Never put ` · ` inside a bullet here, or it reads as a body log line. A research task, for example:
   ```
   ## Outcome

   ### Summary
   We compared three hosting offers for the client portal and recommend the second. It is the cheapest one that keeps the data in the EU, and its support answers within a working day. The report in artifacts/hosting-report.md sets the three side by side, so the client can decide in one read.

   ### Not in it
   - A trial setup on the chosen host: the client decides first.
   ```
4. **A reviewer's word.** If a brief has a Verdict whose first line is not ACCEPTED (REJECTED, or CHANGES with a must-fix list) that no later brief answers, say so in the reply and do not call the work delivered; write `outcome:` only for what was accepted.
5. **history.md.** Append, only in the Steps (never before the gate), `- <time> · delivered · <outcome in a few words> · by <owner>` with the Edit tool (`<time>` is the output of `date +%Y-%m-%dT%H:%M`, run just before this edit, never a guess; owner as in task.md). If the Edit fails with "modified since read", read the file again and retry: a hook appends to it too. Never write `plan accepted`, `preview approved`, `ship approved` or any approval line.
6. **How the work lands.** If the task changed code in the project's repository, read `lands` in `<projects folder>/<project>/project.md` (the frontmatter) and do what it says; do not guess when it is missing or unclear, ask. Reading `Commit and push` means `Merge, then push`. Merging a pull request stays the person's own step, so never merge one.
   The task's branch is per repo: read it from task.md's `repos:` (each item's `name` is the repo, `branch` the task's branch there) and do the choice below in each repo listed. When `repos:` is missing or empty, the task's branch is `GRID_TASK_BRANCH` (the host made it, with its worktree `GRID_WORKTREE`, from `GRID_BASE_BRANCH` in the repository `GRID_REPO`). When `GRID_TASK_BRANCH` is unset too (not a git repo, or a task older than task branches), the task's branch is the current branch of the repository and the base branch is the repository's main branch, as before.
   - `Open a pull request`: push the task's branch and open a pull request. `Draft pull request`: the same, opened as a draft.
   - `Push the branch`: push the task's branch and open nothing.
   - `Merge, don't push`: merge the task's branch into the base branch locally and push nothing. `Merge, then push`: merge it, then push the base branch.
   - `Ask each time`: ask which of the above before doing anything.
   Before acting, per repo run `node "${CLAUDE_PLUGIN_ROOT}/skills/deliver/scripts/land-plan.mjs" "$GRID_REPO" "<lands>"`. When it prints `"fallback":true` the repo has no remote: do the local merge (`Merge, don't push`) without asking, and append `- <time> · land fallback · <its reason> · by <owner>` to history.md. A repo with a remote follows the list above unchanged.
   A merge runs in the repository checkout, every git command as `git -C "$GRID_REPO"`, and only when that checkout is on `GRID_BASE_BRANCH` (`git -C "$GRID_REPO" rev-parse --abbrev-ref HEAD`) and clean (`git -C "$GRID_REPO" status --porcelain` prints nothing); otherwise stop and ask the person with the questions skill. Then `git -C "$GRID_REPO" merge "$GRID_TASK_BRANCH"`, and append `- <time> · merged · <GRID_TASK_BRANCH> into <GRID_BASE_BRANCH> at <short sha of the merge commit> · by <owner>` to history.md (`git -C "$GRID_REPO" rev-parse --short HEAD`). Never remove the worktree yourself, it is your session's own folder: after the turn that records the `merged` line the host ends the session and removes `GRID_WORKTREE` (the branch stays), so the remaining steps run as written. The lands merge never rebases, resets, deletes a branch or stashes, and pushes only for `Merge, then push`.
   Worker branches merged into the task's branch before this follow `## Merging` below.
   Then read `deploys` in the same file. `Don't deploy` or nothing: stop. `Deploy from this machine`: run `deploy_command` from the same file (`make deploy` when it is not set) in `"$GRID_REPO"` (the repository when it is unset), after the merge, only once a Merge choice (`Merge, don't push` or `Merge, then push`) has completed; for `Open a pull request`, `Draft pull request` and `Push the branch` deploy nothing and say nothing is deployed until the person merges. `CI/CD deploys`: do nothing more, the pipeline deploys what was pushed. Say in the reply what landed and what ran. Grid's own data (`project.md`, tasks) stays outside the repository.
7. **Brain proposals.** Read every file in `memory/`. Each line that would help another task (the memory skill's Promotion) becomes `brain-proposals/<name>.md` with `status: proposed`, and a history line `- <time> · brain proposed · <name> · by <owner>` (`<time>` from `date +%Y-%m-%dT%H:%M`). Skip a line a proposal already holds. Never write the brain: when proposals wait, the planner starts `grid-curator` (separate from any reviewer), which curates each into a finished linked note and writes the accepted ones into the brain; no person is asked. Say in the reply how many you proposed.
   People: from the task's synced files derive one proposal per person per task, `brain-proposals/person-<handle>.md` with `level: project`, the entry for `knowledge/people/<handle>.md` under the Grid data folder (never a repo): front matter `membership: <handle>`, links `{to, relation: owns | knows | decides | approves}`, a "Questions about X go to <name>" line, `- <date> answered Q-n on <area> (T-NN)` and `- <date> approved <step> (T-NN)` lines (the last 10 kept), one tendency line only when two or more events show it, and `- "<their words>" (<date>, T-NN)` for a preference the person stated in their own words in an Answer line or `intent.md`. Sources: `questions/<person>.md` blocks in state `answered`, history lines `plan accepted`, `preview approved`, `ship approved` with `by <who>`, and `moved to <who>`. Never record the role (a `membership:` line only), contact details, time online or last seen, life outside the work, judgements of a person's quality or speed, cost per person, or anything from mail or chat signals. A guest (Client): only "answers questions about X, via page/relay" and approvals passed, no tendency or preference lines, project level only. Always `level: project`: the workspace-level person note holds only facts true across projects (name, how to address them, communication rules, membership), never a task id, a dated event, or the person's role, decisions or approvals in one project; those stay in this project's note. An instruction a person gave inside one task stays with that task (a task memory line) unless they said it applies always, and only then is it proposed as a workspace preference. The entry has `type: person` and a one-line `description` (at most 200 characters), so the planner files it under `## person` in `index.md`. When a person is removed from the project, the proposal marks their entry `superseded_by: removed`; never delete it.
8. Tell the person the outcome line and the list of files in `artifacts/`; the brain proposals go to `grid-curator`, not to the person.

Refresh `views/plan.html` in the same turn so Obsidian and other readers see the delivered state: in the blocks the plan-page skill marks `live-status`, `live-next` and `live-needs`, write "Approved and merged <time>" and, after a last-step `ship approved`, "Next: Grid closes the task" (after `preview approved`: "Next: read the result and Close · delivered"), and replace any wait or Approve block with one line saying so; leave the plan body as written. A page with no markers (an older one) gets its status sentence and wait lines rewritten the same way.

After a last-step `ship approved`, leave `status: running`, as the approve set it, and write the `delivered` line (step 5): Grid reads the approved gate and that line, then closes the task itself as `grid`, and the Result tab reads "Shipped ... and closed". Do not set `status: waiting`, do not write a `next` that asks the person to close it, and do not close the task yourself. When the turn ends without the work landed (a pull request opened, a branch pushed, a merge that stopped on a question that does not block), Grid sets `waiting` for the person's close itself. After a last-step `preview approved`, set `status: waiting` and `next` to the person's close ("<owner> reads the result and closes the task"); Grid reads the approved gate and shows the Prototype's Approved card (what merged, and Open the Result) and keeps Close · delivered in the task menu, never the Approve again; closing that task is the person's, in Grid. Otherwise `status` stays as it is, apart from `running` to `waiting` if the next step is a person's. Do not write `runner`, `gate_raised`, `paused`, `lane`, `lane_step` or `lane_round`.

## Merging

This is for parallel worker branches merged back into the task's branch (`GRID_TASK_BRANCH`) in the task's worktree; the lands merge into the base branch is step 6. Merge one branch at a time, in the order the plan gives.

1. Read both sides of each conflict and keep what each meant. When the two sides cannot both hold, for example where a contract, a format or an API changed both ways, stop: that is a person point, written as a question on the task.
2. Never hand-merge generated files (lockfiles, schemas, generated types or routes). Take either side, then regenerate them with a `grid-runner`.
3. After each branch, run the tests of the packages the merge touched, through a `grid-runner`. A failure stops the merge and goes back to the worker's brief.
4. Never push, reset, rebase away work, delete a branch or stash. Record each branch merged, with its commit, in `history.md`.
