## Persistence and compatibility

New `usage/thresholds.json` writes use version 2. A threshold array appears only
for a unit explicitly configured on the task. Budget changes and fired-notice
saves retain the budget, baseline and fired bookkeeping without copying inherited
thresholds into storage. Each read resolves omitted units from the current
workflow, then the built-in defaults. Explicit empty arrays still disable that
unit's notices, including after subsequent budget changes.

Version-1 files remain readable. Every threshold array present in such a file
stays authoritative, even if it equals a former default or workflow value: its
original intent cannot be recovered. Rewriting that file preserves those arrays.
A missing token array in a pre-token version-1 file continues to inherit, including
after rewriting. Existing version-1 required-field and value validation remains.
Version 2 permits absent arrays but rejects explicit nulls and invalid values.
Unknown optional fields remain tolerated.

The storage version is separate from the effective CLI/API configuration: response
version 1, all response fields, workspace token-budget fallback, totals, and
baseline semantics are preserved. Older binaries reject version-2 storage, so
readers of newly saved files need this change. No automatic migration occurs on a
read. Fired entries remain keyed by unit and percentage for the task lifetime;
removing and restoring a percentage does not send its notice again. Existing Feed
recovery after a failed fired-state save is preserved.

Help includes the exact sentence:

> Per unit: a threshold set on the task wins, then the workflow's usage thresholds, then the default.

## Workflow reads

Both `UsageNoticeThresholds` and `GatePostRoles` now use one task-policy reader.
It rejects a symlinked leaf, including dangling links, and uses the existing
cross-platform no-follow opener to reject replacements during opening. Reads
consume at most 1 MiB plus one byte and reject files larger than 1 MiB, including
the Markdown body. Exactly 1 MiB is accepted.

Refusals retain filesystem-error classification. Usage reports a path-free warning
and retains defaults. Gate callers preserve their established handling of I/O
failures, including fail-closed withdrawal writes; malformed-YAML behavior is
unchanged. The existing usage seam validation and policy data source are retained.

Supporting changes are confined to the usage, workflow and CLI packages, their
regressions, and the existing usage-help golden. The shared policy reader is the
small missing piece used by both readers. Module and Makefile contents are
unchanged, and no root DONE.md was created.

## Regression evidence

On the unchanged L114B production base with the new regressions, this command
exited 1:

```sh
go test ./internal/cli ./internal/workflow -run 'TestUsageWorkflowEditsAfterSave|TestUsageWorkflowUnsafeFileDefaults|TestUsageThresholdPrecedenceHelp|TestTaskPolicyFileLimits' -count=1
```

Budget and unrelated threshold saves produced an 80% notice instead of the fixed
workflow's 90%; a first notice save prevented the subsequent 90% notice. Both
readers accepted oversize files and symlinks, including a dangling symlink treated
as missing. Help lacked the required sentence. The CLI regressions also failed on
plugin main `0ebca7c` (which still lacked workflow wiring).

The lane tests cover all three first-save paths, workflow correction, removal and
restoration of a fired percentage, additional percentages, and repeated posts.
Storage tests cover set and explicit clear for each unit, inherited defaults after
workflow removal, budget changes, notice saves, legacy-file rewriting, and corrupt
sparse files. Reader tests cover both policies at and above the size boundary,
symlinks and dangling symlinks; CLI tests verify default notices and path-free
warnings for refused workflows. Existing withdrawal-policy and usage golden tests
also pass.
