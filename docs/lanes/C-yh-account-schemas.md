## What changed

- `contract/schemas/cmd-account-{status,windows,scan,folder,statusline}.json`: closed objects (`additionalProperties: false`) listing every key the writer emits. `signedIn` is `boolean | null` and required, because `*bool` is written as `null` when the provider cannot be asked. `windows[].resetsAt`, `asOf` and `note` are in `properties` only (`omitempty`).
- `contract/fixtures/cmd-account-*/`: 25 files. `valid/basic` and `valid/populated` are the live stdout with the temp root and the clock made synthetic; `valid/signed-in-states`, `valid/signed-states` and `valid/stream-without-reset` are mutations of it; the invalid ones drop a required key, give a key the wrong type, or rename a key. All are written by `yhAcWriteFixtures` in the new test (`make test UPDATE_CONTRACT_COMMAND_FIXTURES=1 "GOFLAGS=-count=1 -run=TestYhAccountStdoutValidates"`), which checks each file's validity before it writes it.

## Findings

- `account list` and `account status` share one writer (`runAccount` routes both at `internal/cli/account.go:47` to `accountStatus`, which writes the `--json` object at :87). The stdout is the same object: `TestYhAccountListIsStatus` validates `list --json` against `cmd-account-status` and compares it with `status --json` (minus the `checked` clock), basic and populated. So `account list` carries the status schema. The only difference is that `list` passes `register=false` and writes nothing.
- The brief lists ten `account scan` fields for the app (`id, kind, name, email, dir, default, signedIn, checked, plan, added`, citing http.go:199-222). In the app at `8f9b806d`, `internal/slices/agentaccounts/http.go:187-194` (`type folder`) is what decodes `account scan --json`: `kind, dir, home, signedIn, email, plan`. The ten-field struct at :212-223 (`type row`) is the app's own page row, built from its settings records and filled with `id, name, default, checked, added` there. `account.Folder` (`internal/account/account.go:93-100`) writes exactly the six keys the app decodes, so no field the app reads is missing and the scan schema lists those six.
- `account windows`: the worker (`internal/kernel/worker/account.go`, the `windows` struct) reads `id, source, windows[].label, used, resetsAt`; the Accounts page relays each entry as raw JSON (`http.go:307-316`). `account status`: the worker reads `id, kind, name, dir, default, signedIn`. `account folder`: the app reads only the exit code (`http.go:254`, :382). `account statusline`: relayed as is (`statusline.go:28-44`). All are in the schemas.
- `kind` is `string` in status and windows (it comes from the registry file) and `enum [claude, codex]` in scan (built from the plugin's own list of kinds). `windows[].label` is `enum [5h, 7d]`; `source` is `enum [statusline, stream, codex, none]` as the writer's comment lists. `added` is a free `string` (the registry's "auto" or "person").
- In the first `account status` run on a fresh machine, an account whose folder `status` has just made is not in that run's scan, so its `signedIn` is `false`; the next run answers `null`. Both are valid values.

## NOT VERIFIED

- Nothing here is a screen. Not verified against a real `claude` or `codex` binary: the tests hide both, so `signedIn` from a provider's own `auth status` answer is covered only by the schema allowing `true`, `false` and `null`.
- Windows and macOS runtime behaviour of the commands is not run; the cross build compiles and vets them.
