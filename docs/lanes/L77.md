## Behavior

The hook environment now propagates both `GRID_ROLE` and `GRID_MEMBER`.
Home approval and hook settings share the existing caller-aware resolver
constructor in `internal/guard/settings.go`; no new exception was added to the
Personal choke test.

Callers allowed Personal by the CLI policy retain whole-home approval. This
includes owners, member/lead sessions without an authenticated member identity,
and recognized machine/worker roles. Member/lead sessions with an identity
retain the CLI's existing Personal refusal. Guests, external callers, and unknown
roles cannot receive approval for Personal or a whole-home directory grant.

For a caller refused Personal, automatic home access is limited to the active
registered project's data directory. The project comes from trusted session
`GRID_PROJECT`/`GRID_TASK` or cwd resolution, never the requested read path.
Project records contain no membership ACL; this lane treats the session's
resolved project as its scope and does not invent a membership database or grant
all registered projects. A sibling project, the projects parent, home-level
files, an unresolved project, and Personal receive no automatic home grant.
Project directory symlinks cannot become session directory grants. Personal
checks cover canonical and relative paths, missing descendants, and symlink
aliases; the existing on-disk case normalization is retained.

Scope denials cannot be weakened by `home-allow=off` or `warn`. Permission
forwarding encounters those denials before contacting the server, and checks
server-rewritten input through the same guards. The legacy plugin-script
shortcut is refused for callers without Personal access, because even an
argumentless legacy script can choose Personal implicitly. Allowed callers keep
its existing behavior. These hooks are permission guards, not a shell sandbox.

`contract.NormalizeRole` is the one helper for trimming, lowercasing, and
removing an optional `grid-` prefix. Personal, trust-tier, caller/writer,
question/feed authorization, guard, hook-agent, orchestrator, job-owner, and
workflow role checks use it. `worker` and `grid-worker` have the same Personal
answer. A bare prefix remains unknown; repeated prefixes do not grant Personal.
Wire-schema role enums are unchanged.

The settings choke test now inspects unqualified `Store` references inside the
settings package, not only imports elsewhere. Existing Store methods operate on
the supplied store; only the CLI `settingsStore` adapter constructs a writable
store. The internal `ReadHookLevels` exception permits only direct
`Store{...}.Effective()` calls. New exported functions, methods, or variable
bindings require review, including writers that use direct file operations.
Mutation cases cover literals, local declarations, aliases, `new(Store)`, new
methods, and direct exported writers.

## Regression evidence

The real CLI entry test `TestHookPersonalScope` failed on merged base `f30cee2`:
guest and unknown-role reads approved Personal, sibling projects, and home-level
paths, and PermissionRequest added the whole home. The tests exercise
PreToolUse, PermissionRequest, and permission-forward with an actual guest
environment. Allowed owner/worker rows and scoped guest project grants are
positive controls.

`TestPersonalRolePrefix` also failed on that base, including `grid-worker`,
`grid-host`, and `grid-cli`. It now checks both spellings of every known role,
case/whitespace normalization, both member identity states, and unknown roles.
Additional tests reject bare and repeated prefixes.

An actual scratch exported writer inside `internal/settings` called
`Store{Home: home}.SetHook`. The old choke test passed with that writer present;
the extended test failed for both the new export and its Store construction.
The scratch writer was removed and its file was not committed.

Guard tests exercise every supported file tool, all home-allow levels, both
permission events, aliases, missing files, relative paths, and legacy scripts.
Traversal and absolute glob patterns are hard denials for restricted callers,
so a deferred glob cannot reach Personal through permission forwarding.
The permission-forward regression uses a test server that approves and rewrites
a read into Personal; the real hook entry refuses it without directory updates.

A disposable archive of merged base `f30cee2` was also replayed with the new
CLI, resolver, guard, and forwarding tests copied unchanged. All four packages
failed for the intended regressions: `TestHookPersonalScope`,
`TestPersonalRolePrefix`, `TestHomePersonalToolsAndAliases`,
`TestHomePersonalLegacyScripts`, and `TestPermissionForwardCannotApprovePersonal`.
