## Inventory conventions and defaults

- Shared flags are repeated per subcommand, without factoring out common
  flags: default, owner may change. No global --home flag is invented; the
  current parsers use Grid home from the environment. Flag names include --.
  Implicit help handling is not a declared data flag. takes describes whether
  a separate value is consumed; --error is a bool-style flag which also
  accepts --error=message. required means unconditionally needed for that
  invocation, not a requirement conditional on another flag or environment.
- Streaming output is one schema per NDJSON line with stream: true:
  default, owner may change. job next is marked streaming for --wait.
  Today it waits for an assignment or wake, writes exactly one JSON line and
  exits. The line is an array of rows, not one Job object per line; a wake
  uses a different object shape. sync has no subcommands or stream metadata
  until it is built, as required for unbuilt commands.
- Exit codes are outside commands.json: default, owner may change.
  feed-contract.md:305-308 (section 13) specifies exit 1 for a held merge
  lease and for live-holder take-over refusal. It names no exit code for
  job next or the other app calls. Take-over is not parsed by this checkout.
  The dispatcher documents 0 success, 1 failure/format refusal and 2 usage
  or unbuilt command (internal/cli/cli.go:140). Feed errors additionally
  return 3 for stale lease and 4 for disk full (internal/cli/feed.go:105).
- A bare array has top-level type array: default, owner may change.
  This applies to task list, session list, intent list and worker list.
  job next uses oneOf because it also emits a wake object.

The parser accepts more flags than some help summaries advertise. In
particular all orchestrator verbs accept the same flags, even where a flag
has no effect; job render/lint/show share task and budget flags; task move
accepts --to; intent renew is built although the command-table summary omits
it. The inventory follows parsing, and preserves command-table summaries
verbatim. Arguments in angle brackets are required, square brackets are
optional, and alternatives explain overloaded operands. task move accepts
a destination operand, or --to with an optional task operand. Session send
and switch accept their value as an operand or a flag.

## Output oddities and setup limits

- task show and task list print absolute paths. Captured fixtures replace
  the temporary home root with <ROOT>. task list omits plan_hash even when
  task show includes it. Owner, owner_role and gate are optional fields.
- The plan hash is six hexadecimal characters, not a full SHA digest.
  Approve returns an audit event and does not itself change waiting to
  running. note and ship gate are omitted unless present. Refusal decisions
  likewise preserve the current task state.
- Session actions return intent records without a completion state, PID or
  session liveness record. Their default target is the task folder name,
  while task move targets the destination worker. Explicit send retry keys
  appear as scoped hashes. Intent list adds state and optional claim/done
  objects; the completed-intent fixture exercises both.
- Session list/show expose persisted timestamps and process identity.
  Missing last_alive and until values appear as year-1 timestamps, not null.
  Optional fields are omitted, including slept and ended when absent.
  task attach supplies session fixtures through the CLI and starts no child.
- Worker list reads app-owned worker.json/worker.lock; it cannot create
  workers. Its nonempty fixture supplies synthetic app input. Presence is
  reported, stale or unknown, not a live process probe. Lock-only input
  produces state unknown and a year-1 updated_at timestamp.
- Feed state contains dictionaries keyed by Job IDs, question IDs,
  references and hosts. Their values are typed while keys remain open.
  Nullable folded Job fields and arrays are preserved. verified is opaque
  JSON copied from result evidence. Feed post returns an envelope, retaining
  nullable lease/re/job/attempt/wake fields and a type-dependent body.
- version --check adds a check object and may add warning; normal version
  handshakes have only version, contract and app_min. A captured offline
  check uses an empty manifest URL and performs no network request.
- task new writes a display ID without a stable Feed ULID
  (internal/task/create.go:92-110), while Feed requires a stable ULID
  (internal/feed/identity.go:54). Therefore a fresh CLI-created task cannot
  run feed state, feed post or job next on this checkout. The requested
  CLI-only setup cannot produce those successful outputs. The existing
  feedHarness contains a compatible stable-ID task fixture; permission to
  reuse it for these cases is pending. No task writer was changed.
- The CLI exposes merge leases only. Assignment fixtures require the
  existing lease.TaskStore API to acquire the task tenure, with Feed
  handover and Job posts still made through CLI calls.
- There is no CLI producer for incoming refusals. The refusal test supplies
  a synthetic refusal file, as existing tests do, then invokes refusal decide.
  No task, plan or Feed record is manually created by the new test.

## Tests and fixture provenance

The new test file reuses newHarness and h.run. It compares inventory order,
summaries and built status to the unexported commands() table, checks output
references and the live contract version, and validates raw stdout against
the published schemas. Unknown-field mutation checks visit fixed objects
inside arrays, nested structures and schema references. Dynamic dictionaries
keep typed additionalProperties. The feed types baseline is a literal byte
capture from the checkout before adding cmd- schemas, compared both to CLI
stdout and contract.PostTypes(). No cmd- schema has x-class or x-roles.

Valid fixtures are captured from real in-process CLI calls on temporary
homes. Identities are synthetic; only temporary paths and process identities
are normalized after validating raw stdout. To refresh the captured examples:

    UPDATE_CONTRACT_COMMAND_FIXTURES=1 go test ./internal/cli -run '^TestContractCommandsApp$' -count=1

Invalid fixtures each delete a required field or replace a field with the
wrong type. Keep at least two of each kind for every schema. The existing
internal/contract TestFixtures discovers cmd- schemas automatically.

Required verification commands:

    make test
    make lint
    GOOS=windows go build ./...
    GOOS=darwin go build ./...
    go test ./internal/cli -run ContractCommands -v
    go test ./internal/contract/...

Windows and Darwin builds and make lint passed. The 18 non-Feed schema
fixture suites, live command cases and unknown-field rejection tests passed.
The full make test run failed on the missing cmd-feed-post, cmd-feed-state
and cmd-job-next fixtures; their live cases are explicitly skipped pending
the setup exception. The unrelated TestEnvironmentCLI also encountered an
occupied dev port during that run and passed when rerun alone. The temporary
folder leak check found no leaks. Full acceptance remains blocked by the Feed
setup exception above; no all-green result is claimed.

## Intended differences and remaining work

This lane adds a checked machine-readable command contract where the app
previously guessed types; this is the hand-off specified by
plugin-design.md:445 and the startup version check in go-architecture.md:164.
It changes no old-plugin command behavior. The row-array and wake outputs
are recorded as implemented, alongside feed-contract.md:307's row fields;
no command is rewritten to match that description.

The unbuilt answer and sync commands have no schemas. The Feed fixture
exception is the remaining blocker to full live-output coverage and the
acceptance checks; all command implementations and concurrent lanes remain
untouched. These notes are the lane completion record; there is no root
DONE.md.
