# L145: `brain accept` runs the proposal check, and `brain check` compares entry hashes with the audit log

Base: main 298aee0f with lane-L138F (7bc2432b) merged as the first commit (49fce400); that merge commit drops when L138 and L138F land and this rebases. Branch lane-L145. Land after L143 and rerun `make generate` after the rebase.

## What changed
- `internal/brain/check.go`: `checkProposal` now reads once and delegates to `checkProposalBytes(level, name, n, b, res)` through the replaceable `ProposalCheck`; `checkScope` ends with the drift check when `AuditHashCheck(level)`.
- `internal/brain/accept_gate.go` (new): `CheckRefusal{Result}` (typed error, text names codes and files only), `AcceptCheckRequired` (key `brain_accept_check_levels`, default home and project) and `checkAccept`.
- `internal/brain/store.go` `decide`: reads the proposal once with `readProposalBytes` and, on accept only, runs `checkAccept` on that `n` and `raw` after the gate and before anything is written, still under the level lock (store.go:362). Reject never reaches it.
- `internal/brain/audit_check.go` (new): `auditDrift`, `AuditHashCheck` (key `brain_audit_hash_levels`, default home and project) and finding `audit_hash`. The log is streamed like `Store.Changes`. Per topic/name the newest hashed, non-rejected line stands for the entry, newest as `Changes` orders it (by stamp, a later line when stamps tie). Legacy lines, rejections, lines that do not parse and entries that are gone give no finding. Accept does not run it.
- `internal/braincmd/command.go`: a `*brain.CheckRefusal` from accept exits 3; `--json` prints `{"error":"check_failed","code":"check_failed","findings":[...]}` on stderr, plain prints the findings as `plainCheck` does, on stderr. Other errors keep exit 1.
- `contract/README.md`: the `audit_hash` code, the accept exit 3 and the two host policies.
- No new verb or flag: `make generate` leaves no diff.

## Decisions
- **No `skill_field`, `skill_shell` or `agent_field` accept rows.** No accept path reaches skills or agents: `skills` is a reserved topic (internal/brain/topics.go:63), `agents` is a config topic the gate refuses (store.go:454), `Parse` is strict about front matter keys (markdown.go:27) so a proposal cannot carry `allowed-tools`, and L138 does not inspect prose (`checkProposalBytes` decides on `topic` only). Those three codes come from `checkSkills` and the agents loop in `checkScope`, which scan published files and run for `brain check` with no id.
- **`config_topic` in Accept: the gate refuses it first**, so the existing behaviour is unchanged: exit 1, proposal marked `rejected` (store.go:337, store.go:454; reserved `workflows` fails in `topicAt`, topics.go:63). The accept-time check runs after the gate (store.go:362) and never sees a config topic. `TestConfigTopicStillRefusedByGateNotCheck` pins this.
- **Same bytes.** `decide` and the check use one read (`readProposalBytes`); `checkProposal` was refactored to delegate to a bytes-based function (check.go:167-180) so that needs no second read. The published note is `Encode(n)` of that same `n`.
- **The accept-time check catches nothing but `config_topic` today**, which the gate already refuses. It is the structural hook for any future code a proposal can carry. The rows that drive it use the replaceable `ProposalCheck` with a stand-in that returns a finding.
- `ProposalCheck` is exported so the braincmd tests can replace it; it is a host seam like `AcceptCheckRequired`.
