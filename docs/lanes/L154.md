# L154: `grid approve --gate` binds an approval to the gate the person saw

Base: ref main 91ca0950 (L151a and L151b landed). Branch lane-L154. Decision: an approval names the gate it approves (default, plugin first; the app sends the gate in a later batch).

## What changed
- `internal/task/write.go`: `WriteOptions.Gate` ("", plan, preview, ship). `internal/land/approval.go` passes `o` through unchanged, so it needed no edit.
- `internal/task/gates.go` `Store.Approve`:
  - Any other `Gate` value is `ErrEditUsage` (exit 2), checked next to the token policy, before `withWrite` takes `.task.lock` or replays a journal.
  - Under `.task.lock`, after the waiting check, the effective gate is computed as before (`ship`, `preview`, `plan` for anything else) and a named gate that differs is refused with `Changed since you approved: the task is at gate <g>, not <want>` (exit 1), before `.plan.lock` and before any write.
  - Repeat: after the token check, when the receipt for that gate already matches (task, `what: approve`, plan hash, digest, the gate's own `gate` field and the lands hash), `Approve` returns the stored event and writes nothing: no receipt rewrite, no approve event and no second `preview approved` line. All three gates. A stale token still fails with `plan hash no longer matches`; a legacy receipt without a digest, a receipt bound to another deploy rule, or one misfiled under another gate is still rewritten.
- `internal/cli/task_write.go`: `--gate` flag and usage line.
- `contract/README.md` (approve section, the `task_write.go` line reference), `docs/delivery.md` ("The gate a person saw"), `contract/commands.json` (regenerated: `--gate`).

Fallback not needed: no existing row pins the receipt rewrite on repeat (task, land, cli, plan, job, guard and orchestrator suites green with the no-op).
