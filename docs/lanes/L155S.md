# L155S: the shared plan hold resolves named workflows

Base: main 91617acc. Branch lane-L155S. Code head 747fc89b; the final head differs from it by this report only. lane-L155 899e8d0 was read for its resolver logic and tests, not cherry-picked.

## Why
`task.PlanStage` and `task.PlanHeld` (hold.go:27 and :67 on main) read the steps with the inline-only reader. Tasks made by `grid task new` carry `workflow: <name>` or `''`, so every current-format task read as "unreadable" (held), and the receipt branch always required a plan approval. The guard and Deliver both held a named-workflow task that was past its plan gate, or whose template has no plan gate.

## Changed
- internal/task/hold.go:
  - `StepLookup` is the lookup type.
  - `StepsFor(r, dir)` is the one lookup constructor. It calls `workflow.TaskSteps` with the project folder above `tasks/`, so it covers an inline list, a named template (the project's copy first) and the workspace default (the project's copy included). It resolves the text it is given and never re-reads task.md.
  - `InlineSteps` is the old reader.
  - `PlanStageWith(lookup, text, history)` returns "unreadable" on a lookup error.
  - `PlanHeldWith(lookup, dir, text, history)`: its receipt branch asks `approvalRequired(lookup(text))`. That mirrors `taskfile.PlanApprovalRequired` on the resolved steps and returns true on any error.
  - `PlanStage` stays as the inline-only wrapper, for the hook helpers.
  - `PlanHeld` is removed: once Deliver moved over, it had no caller left.
- internal/task/deliver.go:191: `PlanHeldWith(StepsFor(d.s.Resolver, d.dir), ...)`. It is still asked last, in the dry run and in the re-check under the locks.
- internal/guard/context.go:
  - `stepsFor(env, dir)` is `taskstore.StepsFor(callerResolver(env), dir)`, the same constructor Deliver uses. Both resolvers carry the caller from the environment, so a guest whose project is filtered gets the same answer from both.
  - `held(lookup, dir, text, history)` calls `PlanHeldWith`.
  - `planStageWith` is added.
  - `isHeld` is now a context method.
- Outside the two files the brief names, these changes were forced by the `held` signature, plus the proposed-edit path:
  - internal/guard/plan.go: `held` at :47, `c.isHeld`, and `leavesPlan` takes the lookup and resolves the proposed text (:192-199).
  - internal/guard/recall.go:39: `held`.
- Existing tests, signature only: `stepsFor(f.env, f.task), ` was inserted into `held(...)` at internal/guard/deliver_hold_test.go:67, :82 and :105, and at write_hold_test.go:42. No assertion was changed.

## Inline-only callers that stay

It fails closed: a named or empty workflow reads as "approval required", so plan publication waits for an approved digest. This is over-strict for a template with no plan gate, but it is never a release.

- internal/hook/brain.go:199, `guard.PlanStage` in the recall hook. It decides only whether brain recall hits are shown, not a write: "unreadable" still shows them. internal/hook was outside this lane's files. Note: `o.Resolver` is available there, so a follow-up could move it to `PlanStageWith`.
