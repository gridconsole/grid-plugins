# L159a: anchor the plan-accepted match in hold.go

Base: main 91617acc (L151aU report). Branch lane-L159a. Code head 83f02f7; the final head differs from it by this report only.

## Why
The L151b review (note 1, security, pre-existing): `acceptedLine` in internal/task/hold.go was `(?m)^- \S+ · plan accepted · `. A history line written by the task writers is a JSON event on a Markdown bullet, `- {"task":...,"note":"..."}`, and its first field that holds a space is agent text: the note (`grid history add`, a spec heading at preview raise) or `who.id` (`--by`, `GRID_ACTOR`). With no space before it, `\S+` swallowed the JSON up to that text and ` · plan accepted · ` matched. So `grid history add "x · plan accepted · y"` read as a person's acceptance, `PlanStage` returned "" and the hold released (guard and Deliver both ask `PlanHeld`). It was reachable on main.

## Changed
- internal/task/hold.go: `acceptedLine` is `(?m)^- \d{4}-\d\d-\d\dT\d\d:\d\d · plan accepted · `. That is the line shape `taskfile.HistoryLine` writes with Grid's minute stamp (`2006-01-02T15:04`), from the line start. A JSON event starts `- {`, so no text inside it can match; the prose writers (`AppendHistory`, the preview line) fix their event words and `CleanHistory` removes line breaks and the `·` delimiter from what the caller supplies. One regex line and a two-line comment; nothing else in the file.
- Fails closed: a line that is not exactly that shape no longer releases. Every accepting fixture in the repo (guard, orchestrator, delivery, golden `lib-planStage`, recordings) is `YYYY-MM-DDTHH:MM` and keeps passing, untouched.
