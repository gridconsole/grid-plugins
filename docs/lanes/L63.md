# L63: Windows file locks

Implemented on `lane-L63`, based on `f39661a`, using only the standard library.
Changes are limited to `internal/fslock/fslock_windows.go`, the package comment
and `ErrUnsupported` text in `internal/fslock/fslock.go`, Windows tests, and this
note. `go.mod`, `go.sum`, the Unix implementation/tests and `fslock_other.go` are
unchanged. L50's process probe and `lease take` work remains separate.

## Implementation

`LockShared` uses `LockFileEx` with flags zero; `LockExclusive` adds
`LOCKFILE_EXCLUSIVE_LOCK`; `TryLockExclusive` also adds
`LOCKFILE_FAIL_IMMEDIATELY` and maps `ERROR_LOCK_VIOLATION` (33) to `ErrLocked`.
`Unlock` uses `UnlockFileEx` on exactly the same range and ignores errors.
Closing the handle also releases its locks. The DLL procedures are resolved
with `syscall.NewLazyDLL("kernel32.dll")`; no `golang.org/x/sys` dependency was
introduced.

Windows byte-range locks are mandatory. Every operation reserves one byte at
offset `0x7FFFFFFFFFFFFFFE`, represented by `OVERLAPPED.Offset=0xfffffffe` and
`OffsetHigh=0x7fffffff`. This keeps the content available through other handles
and does not extend the file. Callers cooperate on that byte just as Unix callers
cooperate on `flock`. See Microsoft's [LockFileEx documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex).

Each operation owns a manual-reset event. Although current callers open
synchronous handles, `ERROR_IO_PENDING` is handled with
`GetOverlappedResult(..., TRUE)`, which waits on that event and checks completion
before releasing the event or `OVERLAPPED`. `SyscallConn.Control` keeps the file
alive and prevents concurrent close from recycling its handle during the call.
The Windows test suite also supplies a deliberately asynchronous raw handle to
exercise pending completion. See [GetOverlappedResult](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getoverlappedresult).

`OpenNoFollow` uses `syscall.CreateFile` with `FILE_FLAG_OPEN_REPARSE_POINT` and
`FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`. Every successful open
is checked with `GetFileInformationByHandle`; any final-component reparse point
is closed and refused as `*os.PathError` wrapping `syscall.ELOOP`. This preserves
the `errors.Is(err, syscall.ELOOP)` check at
`internal/artifact/open_unix.go:18` (that caller also accepts `EMLINK`). The Unix
open supplies `O_NOFOLLOW` at `internal/fslock/fslock_unix.go:32`.

No caller opens a directory through this API, so `FILE_FLAG_BACKUP_SEMANTICS` is
not set. Directory junction opens can fail with `ERROR_ACCESS_DENIED` before a
handle exists. In that failure case only, `GetFileAttributes` identifies a
reparse point and refines the error to `ELOOP`; the function never retries by
following the link. This path cannot authorize an open based on a path lookup.
Successful opens always use the handle check.

Access maps `O_RDONLY`, `O_WRONLY` and `O_RDWR` to their Windows rights.
`O_CREATE | O_EXCL` uses `CREATE_NEW`, `O_CREATE` uses `OPEN_ALWAYS`, and other
opens use `OPEN_EXISTING`. `O_TRUNC` truncates the checked handle afterward:
`CREATE_ALWAYS` is incompatible with `OPEN_REPARSE_POINT`, and truncation must
not alter a refused link. See [CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).
`O_APPEND` grants write rights without `FILE_WRITE_DATA`, so writes append even
after seeking backwards. For `O_TRUNC | O_APPEND`, a temporary write-capable
handle is truncated and duplicated with reduced append rights to the same file
object, avoiding a second path lookup. The result is returned with `os.NewFile`.
Creation permissions preserve Windows' read-only attribute convention; `O_SYNC`
requests write-through.

| `GOOS=windows go build ./...` | Passed |
| `GOOS=windows go vet ./internal/fslock/` | Passed |
| `GOOS=darwin go build ./...` | Passed |
| Windows test compilation for every package | Passed, 60/60 packages; each `go test -c` used a unique output path under `/tmp/L63-windows-tests` |
| `git diff f39661a -- go.mod go.sum internal/fslock/fslock_unix.go internal/fslock/fslock_unix_test.go internal/fslock/fslock_other.go` | Empty |

The first attempt to compile all Windows tests into one directory was rejected
by Go because `contract` and `internal/contract` both produce `contract.test`.
Compiling each package to a distinct filename resolved this tooling collision;
it was not a Windows source build failure.

No Windows host was configured or reachable through the provided execution
environment. `cmd.exe`, `powershell.exe`, `wine` and `wine64` were absent, and no
remote Windows execution target was supplied. **Windows tests were compiled,
not run.** No native Windows runtime pass is claimed. On a Windows host run
`go test -count=1 -timeout=2m ./internal/fslock/`.

The Windows tests cover exclusive/exclusive, shared/shared, shared/exclusive and
exclusive/shared compatibility; nonblocking contention and success after unlock
and close; unlocked content I/O through a second handle; pending I/O completion;
and a re-executed child that holds the lock until killed. The child has a
`t.Cleanup` handler that kills and waits on every failure path. Open tests cover
all caller flag combinations, missing files, `O_EXCL` returning `os.ErrExist`,
append after seek, truncation, rename/replacement while open and locked, file
symlinks (including dangling links), and junctions created with `cmd /d /c mklink
/J`. Symlink creation skips with the privilege error; junction creation skips
with command diagnostics if unavailable. Native execution is needed to establish
those tests' results and any skips.

was available, the following are source-audit findings and risks, not observed

| `internal/atomicfile/atomicfile.go:39`; readers at `internal/settings/store.go:63` and `internal/task/write.go:96` | Atomic replacement can fail while a reader holds an ordinary Go `os.Open`/`os.ReadFile` handle without delete sharing.
