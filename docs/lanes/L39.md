# Lane L39: Feed-backed questions

Built the top-level `grid answer <task> Q-N "text"` command, removed its nested alias and attribution flags, and made question files recoverable projections of the Feed. Add and answer use the caller's fence-0 writer; answers reference the Feed question ULID. Add, answer, tick and the new `grid question sync [task]` reconcile missing, corrupt or hand-edited files. The existing question lock and atomicfile helper protect projection writes. No protected Go package or go.mod was changed; cli.go changes only register commands and their descriptions.

The question-file schema now carries optional Job and plan item, required question post ULID, history post ULIDs and caller roles, optional options and a conditional recommendation. The file gate is the posted person gate. The question post also retains recommendation and aging metadata for recovery. Guests can answer only questions addressed to them; team roles may answer any recipient's question. Existing host and question-file guard rules remain unchanged; refusal text names the supported answer command.

The Feed adapter closes person gates with a single distinct eligible answer and preserves explicit task-control selection for imported conflicts. Withdrawal and aging have Feed control events and recover with the files. Due defaults release gates on reads; tick can add a default audit control. Those writes require an existing task lease and handover, using GRID_LEASE and GRID_LEASE_EPOCH; fence-0 answers require neither.

## Limits and reasons

- The protected internal/contract fold still requires explicit answer selection. The person-gate behavior is implemented as a separate layer in internal/feed around that fold; direct contract.Fold callers retain the older semantics, and its verdicts are preserved unchanged. No lease rule was weakened. Withdrawal/tick callers need a task tenure because controls are lease-bound under `docs/feed-contract.md:85`.
- Automatic ticks on every command/hook/worker pass and Job resumption are not wired here: they require dispatcher/Orchestrator integration beyond command registration. This lane updates question and Feed projections without issuing Job status controls. Sources: `docs/go-architecture.md:25`, `docs/brain-feed.md:218`.
- No legacy migration or stable task-id backfill is performed. Existing Feed requirements apply; old file-only L22 and recipient-file data remain untouched and need migration before their decisions can be changed through the Feed. UI rendering, landing summaries and task/history planner edits remain separate consumers. Sources: `docs/brain-feed.md:33`, `old-plugin/skills/questions/SKILL.md:8`, `old-plugin/skills/questions/SKILL.md:48-50`.
- Native macOS and Windows tests were unavailable in this Linux workspace. Both required cross-builds pass; locking and no-follow handling use the existing platform helpers.

Work is committed in small steps on the supplied current branch; no branch switch or merge into another branch was performed.

## Rework after review

Only owner, member, lead and an addressed guest can answer a person gate. Agent and CLI answers remain legal raw Feed records where the shared contract permits them, but cannot close a person gate, including through explicit selection. The answer command refuses those roles before publication, including identical retries. CLI and agent roles remain available for lease-protected control events.

The Feed person-gate layer updates question status and its Needs you and Job indexes without changing any contract verdict. A default whose deadline has passed releases the gate using the read clock and the existing question record. It needs no tick or control record. A later tick may append one default audit event under the task lease; late human answers still apply. No synthetic Feed post or author is invented for a deadline-only default.

List is read-only, including Feed caches: it takes no question lock, creates no directory, and repairs no projection. Add, answer, tick and sync retain the existing fslock and atomicfile write paths. An unbacked Q-N.md is listed by id and the state "not in the Feed"; its contents are neither parsed nor rewritten. Its filename reserves the id even when feed/ is missing. Mutating that question is refused until it is migrated. Backed files still recover on sync and mutation.

All Feed timestamp parses in the question adapter return errors. Withdraw and tick help names GRID_LEASE=task and GRID_LEASE_EPOCH. The guard refusal names grid answer and grid question withdraw, without changing its command matching rules.

Regression coverage includes raw agent/CLI Feed answers, rejected non-person selections, unchanged contract verdicts, deadline-only defaults, CLI tick audit events, byte-identical file-only questions across list/add/answer/tick/sync, missing Feed directories, id reservation, and read-only listing of missing or damaged projections. The rework changes no protected package or schema.

## Second rework after review (L39R)

Rebased onto main after L34, L40 and the Feed MCP server landed. L39's two-value fold is now `feed.FoldReadQuestions`, so it no longer collides with main's contract-only `feed.FoldRead`. The Orchestrator snapshot (`orchestrator.Load`) folds with the person layer through `feed.FoldReadAt` at the store's clock, and `answers()` posts a selection control only for an answer `feed.PersonAnswer` admits. An agent answer therefore neither assigns a Job waiting on a person gate nor makes each pass post a control. The host guard refuses `grid feed post --type answer` in every Go flag form (`--type answer`, `--type=answer`, `-type answer`, any order or quoting) with the same refusal as `grid answer`. This holds when GRID_ROLE is unset, where the CLI writes as member, a role a person gate admits. `question.List` reads question files directly for a task whose task.md has no ULID (tasks made by `grid task new`), so `grid task attach` counts their open questions; only a failed read is an error. DONE.md is gone.

- Not fixed here: the Feed MCP `feed_post` tool accepts `type: answer` with the same default member role, and the Bash guard never sees MCP calls, so an agent session can still close a person gate through MCP.
