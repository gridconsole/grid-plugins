# L160: an agent's Bash write to history.md must not release the plan

Base: main 91ca095 plus L159a. L159a (lane-L159a, eae5924) is not on main and main moved past its base, so a branch on top of it would not contain main. Lane-L160 is main, then L159a's two commits cherry-picked (65006ff, 46661a8), then the two L160 commits. When L159a lands, a rebase skips the duplicate patches.

## Defect
On a task with no approval.json, an agent's `echo '- <time> · plan accepted · x · by person' >> <task>/history.md` through Bash was allowed by the real pretooluse hook, and `PlanHeld` then read the prose line as an acceptance. history.md was in neither protected list.

## Fix (a): done
- internal/guard/host.go: `gateName` names history.md (the textual layer, like task.md), `historyAt` is new, and `gateReason` lists history.md.
- internal/guard/host_targets.go: `writeScan.protected` refuses a path that is a task's history.md (redirects, tee, sed -i, cp/mv, dd of=, globs, cd then write), and `hostProtectedNames` names history.md (glob or expansion before the name).
- Bash only. `gateFile` and `gateAt` are untouched, so the file tools keep their own reasons from the plan guard and the only-writer guard. Reads (cat, head, tail, grep, wc, ls) stay allowed. Grid's own writers (the plugin binary, `grid history add`) are unaffected.
- Cost, same as task.md today: any non-read Bash command that names a file called history.md while GRID_HOME or GRID_PROJECTS is set is refused, wherever the file is (for example `git commit -m "fix history.md"`, or `grid history add "..history.md.."`). Not pinned by a row.

## Fix (b): not done, no safe rule
The brief asked for the narrowest rule that keeps migrated tasks working. I tried the one candidate that could survive: a prose acceptance counts only when no `- {` JSON event line precedes it (scratch copy, not in the lane). It turned red, with the lane's own tests otherwise green: L159a's `TestPlanAcceptedReadsOnlyTheDatedProseLine/prose_line_after_a_forged_event`, `TestEventLineFromTheWriterDoesNotReleaseTheHold/{note,actor}`, and my new row's positive control. Those rows pin that a prose line appended after a Go-written event releases. And a task fresh from `task.Store.New` has no JSON line in history.md at all, so it is byte-for-byte the shape of a legacy task: `cli/delivery_test.go:acceptPlanInHistory` (a Go-created task plus an appended prose line, with no approval.json) only passes for that reason. Rules keyed on task.md format, a hash or a date break the hand-written guard fixtures (`guard_test.go:14`, `approval_test.go:118`) or are forgeable by the same agent. There is no in-band marker, so I kept (a) only. contract/README.md:895 already says legacy approvals stay weak until reapproved; (a) is what keeps an agent from writing one.
