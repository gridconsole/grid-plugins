# S3: four Job states and a queue order

## What changed
- `internal/contract`: `StateOf` maps a stored status to Not started, Started, Needs review or Done (cancelled reads as Done with reason "cancelled"). The fold sets `state` and `state_reason` on every Job in `grid feed state`, and carries an optional `order`. Stored status values are unchanged.
- Order: `job.Job` has an optional `order`. A control record `{target, order}` changes it; the fold applies it only to a Job that is Not started and ignores it otherwise. No older record is edited.
- `orchestrator.Ready` sorts the ready list stably: lowest order first, Jobs without an order after, in the existing posting order. Ties keep posting order. `grid job next` follows it.
- CLI: `grid job post --order <n>` and the new `grid job order <id> <n>` (refuses a Job that has started). `grid job show --json` carries `state` and `state_reason`.
- Schemas: `job-record` (order), `control` (an order-only branch), `cmd-feed-state` (order, state, state_reason; none required, so old output still validates). `contract/commands.json` regenerated by `make generate`.
- Tests added: `internal/orchestrator/order_test.go`. Two rows were added to existing test tables (`contract_inventory_test.go`, `guest_parity_test.go`) because they require every new route to be listed; no existing assertion was changed.

## Status mapping
Not started: posted, ready, parked, stale, rejected. Started: assigned, running. Needs review: submitted. Done: accepted, cancelled. `integrated` (in the control schema, not in the Status constants) maps to Needs review; `conflict` (same) and any unknown status read as Not started.
