## Problem and result

The task approval token policy existed in the task store but was unreachable
from the CLI. `runApprove` now reads the task's `workflow.md` front matter and
passes `PlanHashToken` through the existing land approval store. The workflow
key is `plan_hash_token`: `any` is the replaceable default when the file or key
is missing; `digest` requires a supplied token to be 64 lowercase hex digits.
An invalid value, malformed front matter, or read failure refuses approval with
exit 3 and `workflow.md: plan_hash_token must be any or digest`. Errors expose
neither the path nor the invalid value. Nothing asks the owner.

The existing task gate still rejects a short token under `digest` with exit 2
and `grid: invalid task edit: plan_hash_token digest requires 64 lowercase hex digits`.
Token omission and all other existing task-gate semantics are unchanged.
The person gate remains before task resolution and workflow loading; task access
checks still precede policy reads. Refusal tests verify unchanged task bytes and
no approval receipt. The approval store and its lock order are unchanged.

Task show adds optional `plan_digest` to JSON and an adjacent `plan digest:`
text line. Both tokens use the same single `plan.Store.Read` snapshot and the
existing `plan.Hash`/`plan.Digest` functions used by plan hash. Existing fields,
the source of task data, and no-plan behavior are preserved. The schema accepts
only 64 lowercase hex digits for a present digest. Approve help names both token
forms, both discovery commands, and the workflow policy. The contract's
plan-hash section now says a receipt without `plan_digest` does not authorize
work; explicit reapproval writes a digest receipt, subject to token policy.
