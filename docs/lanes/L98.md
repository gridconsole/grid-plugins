## Membership source and behavior

The existing file is `projects/<project>/project-roles.json`. Its `people`
array names members and guests by `id`; `perm` carries the displayed role
(including `Member` and `Client`). Pending `invites` and role `holders` are
not active project membership. No new membership file or writer was added.

Sources inspected:

- App commit `2a5b8e6fd0dff4b143a8109d5f8019b645b0fb82`,
  `internal/slices/projectroles/read.go`: the projectroles slice reads this
  file and `people[].id`. This snapshot has the reader, not a projectroles writer.
- Rust reference `crates/grid-desktop/src/writes_roles.rs`, Git blob
  `19afdc225f6e8f28bd27a65c2992e96ceded64dd`: the writer persists the same
  roles document; `end_access` and `remove` remove the person from `people`.
- Rust reference `crates/grid-desktop/src/reads_project.rs`, Git blob
  `a663c9bd50a40a61270e4c40c05158bdc06ebad6`: `ROLES_FILE`, the 1 MiB limit,
  and case-insensitive person-ID matching. The local owner's synthetic viewer
  fallback is deliberately not a guest invitation.

`where.Resolver` checks the trimmed caller identity against this people list
for guests. Missing identity, missing/invalid/unreadable membership, invalid
UTF-8, oversized files and symlinked membership grant no access. Reads use the
existing bounded, root-confined safefile helper. Membership is read again on
each lookup, so ending access takes effect without a cached allowance.

`TasksDirs`, registered-project loading, explicit project names/IDs, task
paths/IDs and implicit resolution all apply the restriction. Uninvited records
are filtered before reading their metadata, so malformed hidden records do not
disclose themselves. Guests cannot discover a new, unregistered project through
folder/git inference. Task roots and ID-resolved task paths cannot cross project
boundaries through symlinks. Owner/member behavior and Personal policy remain
unchanged.

Unknown and uninvited explicit projects return the same unregistered error
category and message format (echoing only the supplied selector). Trace and
task CLI lookups have identical exit code, stdout and stderr for unknown and
uninvited selectors; hidden and unknown task paths return `task not found`.

## Scope and regression coverage

The referenced `trace_test.go:106` guest row is absent from this base; that line
is in `TestJobTraceIgnoresAnchor`. `TestJobTraceGuestProjects` now explicitly
asserts zero rows for a guest without invitations and alpha only for an invited
guest, alongside unchanged owner/member results and name/ID filtering.

Resolver coverage includes all six resolution rules, empty/case-normalized
caller identity, revocation, pending invitations, malformed membership, hidden
malformed project records, symlinks, and unchanged owner/member task roots.
CLI coverage checks project listing, invited task lookup, and unknown/uninvited
trace and task results in both plain and JSON modes.

Necessary changes outside `internal/where` and the trace test:

- `internal/projects/projects.go` uses the resolver's filtered registry and
  skips uninvited records before safety checks. Trace's project-ID lookup uses
  this store, so filtering task roots alone would leave an ID bypass.
- CLI fixtures in `feed_test.go`, `personal_bypass_test.go`,
  `personal_guard_test.go`, `settings_access_test.go`, and `task_operand_test.go`
  now explicitly invite their existing guest identities. Feed's fixture also
  preserves the question tests' distinction between project membership and
  who may answer a particular question. The Personal-only resolver matrix uses
  a member; the new guest matrix covers invitation policy across all rules.
- `internal/question/withdraw_cli_test.go` invites its guest so the existing
  withdrawal-permission assertion still reaches that check. The initial full
  suite caught this fixture returning task-not-found before its expected role
  denial; the assertion and production withdrawal behavior were not changed.
