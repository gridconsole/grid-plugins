# L151aS: a task.md write may never change the workflow the reader sees

Base: lane-L151a bf503e43, rebased onto ref/main af68c214 (clean). Work branch `L151aS-work` (the name lane-L151a was held by another worktree); it goes to lane-L151a with `--force-with-lease`. Code head d24bd609; the final head differs from it by this report only.

## Why
`rewriteTask` (Change, Deliver) refused only when the reader saw a list before the write. A list the reader cannot see (items at column 0; a flow list on the line after `workflow:`) reads as `""`, so the task is held for plan approval; the dump turned it into an indented list the reader can see, and `PlanApprovalRequired` flipped from true to false. L151aR note 1 and 2.

## Changed
- internal/task/write.go `rewriteTask`: after the dump, `ParseFrontmatter` the output and compare the reader's `workflow` value with the one before, whatever its type (`sameWorkflow`, `reflect.DeepEqual`; an absent key is nil, a present key never is). Any difference, or an output that does not parse, refuses and writes nothing.
- Must-fix 2: the refusal says how to fix it: "task.md workflow list is not readable as written; indent each item under workflow: (for example \"  - {step: build, kind: run}\") or remove the list, then retry; nothing was written". It still contains "workflow list", so the existing row that matches it is untouched. No current caller of `rewriteTask` edits `workflow`, so the list-shaped hint is the one a caller can reach.
- Beyond Must-fix 1, say so: the refusal also fires when the reader's `Odd` flag differs before and after (second error, "has a __proto__, constructor or prototype key ... remove the key"). `Odd` makes `WorkflowSteps` return nothing, so a task held by e.g. `next: {__proto__: x}` was released when Deliver replaced `next` (PlanApprovalRequired true -> false). Same class of hole; drop the `fm.Odd != after.Odd` block and its row (`TestDeliverRefusesToDropTheKeyThatHoldsATask`) if it is not wanted.
