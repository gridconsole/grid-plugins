# L113: token usage notices at 80 and 100

Branch: `lane-L113`. Plugin main base: `ed6229343655ef2b6c4a59c0e3f304eb08e0fc1f`.
The requested branch reset used `origin/main`, which matched that base. L109's
workspace budget implementation and lane report were present on main; no
unlanded dependency was used. Validated implementation head:
`0f0b2091f521102d4beb98140ca244c133bcf036`. This report is a documentation-only
follow-up to that head.

## Problem and result

Fresh configurations and older version-1 files without a token threshold field
both defaulted to 50, 80 and 100. Both now obtain token thresholds from the same
`defaultTokenThresholds` definition: 80 and 100. Each configuration receives its
own slice. Dollars and minutes retain 50, 80 and 100.

The workflow key is **`usage_notice_thresholds`**, with per-unit `dollars`,
`minutes` and `tokens` thresholds. The seam is
`Store.UsageNoticeThresholds *NoticeThresholds`, nil by default. Within the
struct, nil leaves that unit's built-in default and an empty slice disables its
notices. Supplied percentages are copied, sorted, deduplicated and validated
with the existing percentage rules. Configure this field before concurrent
Store calls. This lane does not read `workflows.md` or change `internal/workflow`.

Precedence is task `thresholds.json`, then the workflow seam, then built-in
thresholds. A legacy file omitting tokens uses the workflow token default when
supplied. Required fields and explicit nulls retain their existing validation.
An explicit task list containing 50 remains authoritative, as does an explicit
empty list. Config, Configure and posting all use the same configuration source.
As before, configuration writes and fired-notice saves persist the full effective
threshold lists; those saved lists subsequently take task precedence. There is
no migration of existing task settings. Invalid supplied workflow settings are
reported as configuration errors; posting still records usage and returns a
notice warning, matching the existing invalid-task-configuration behavior.

The existing posting lock, baselines, fired map and Feed recovery are unchanged.
Tests cover totals 60, 85, repeated 85, 100 and 101: the new defaults emit only
80 and 100, once each. Existing 50 and 80 notice files survive a run byte for
byte, including recovery after a simulated pre-configuration-save crash. The
100 notice does not hold the task; that remains the separate token-limit work.
