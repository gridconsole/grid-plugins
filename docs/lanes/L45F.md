# Lane L45F

`job.Job.Record()` encodes a contract-facing Feed body from a plan-loaded Job.
It removes `follow_up`, omits known brief-only statuses, writes nil `posts_back`
as `[]`, and omits zero `verify.min_tests`. It preserves the optional `kind`,
`visible`, `irreversible`, and `review_reason` fields. Validation stays with
`internal/contract`, including the existing validation on Feed posts.

The projection works on a value copy. Ordinary Job JSON, `job.yaml`, brief
metadata, rendering, and their goldens retain their existing bytes. No schema,
fixture, contract implementation, plan implementation, or Orchestrator changes
were needed.

## Status policy

The old brief lifecycle is defined in `old-plugin/skills/brief/SKILL.md:30`.
It is not evidence of a Feed transition. The record status enum is defined in
`contract/schemas/job-record.json:478`; the Feed starts new Jobs as `posted`
regardless of the omitted brief status (`contract/README.md:156`).

| Job status | Record status | Reason |
| --- | --- | --- |
| Empty | Omitted | Status is optional. |
| `briefed` | Omitted | A written brief proves neither a Feed post nor readiness. |
| `running` | `running` | The same running state exists in both vocabularies. |
| `done` | Omitted | A finished brief does not establish submission, integration, or acceptance. |
| `blocked` | Omitted | A blocked brief does not establish a Feed parking decision. |
| Other contract enum values | Unchanged | Already expressed in the contract vocabulary. |
| Unknown values | Unchanged; validation fails | The projection must not hide invalid statuses. |

There are no renamed status mappings. In particular, the old Feed control
`done` to `accepted` change (`contract/README.md:131`) does not authorize mapping
a brief's `done`: result arrival alone is not acceptance
(`contract/README.md:143`).

## Intended differences from the old plugin

- Brief `follow_up` remains available to brief readers but is absent from Feed
  records. The old brief requires it (`old-plugin/skills/brief/SKILL.md:32`);
  the planned/run Job wire fields do not (`docs/job-contract.md:13-55` in the
  reference specification).
- Brief statuses are projected according to the table above rather than copied
  as Feed state (`old-plugin/skills/brief/SKILL.md:30`; reference
  `docs/feed-contract.md:225-226` assigns mechanical transitions to the loop).
- The Feed body uses an array for `posts_back` and distinct command/kind verify
  shapes, while brief serialization stays compatible. The reference specifies
  `posts_back` at `docs/job-contract.md:54` and verifier alternatives at
  `docs/job-contract.md:68-71`. A command still requires positive `min_tests`;
  invalid nonzero counts on kind verifiers are preserved and rejected.

Reference paths above are relative to the read-only reference tree; `contract/`
paths are in this repository. These are all intentional compatibility changes
in this lane, confined to the new Feed projection.

## Tests and scope

The new round trip copies `testdata/job/task` into a temporary home, selects
J-1 with `job.LoadPlan`, and validates `Record()` before and after setting all
four optional fields. Invalid visible and explicitly empty review reason fail
at `$.visible` and `$.review_reason`. The optional Go string uses an empty value
for absence, so the explicit empty reason test inserts `""` into the projected
JSON body; the zero-value Job field continues to omit it.

A discovered table covers every Job in every `testdata/**/plan.md` (currently
J-1 in `testdata/job/task`). Additional tests cover all status enum values,
unknown statuses, populated and nil `posts_back`, all three verify branches,
and invalid mixed branches/counts. The CLI test posts the loaded Job's record
with `grid feed post`, checks the persisted body with `grid feed read --json`,
and verifies J-1 and its counted verdict in `grid feed state --json`, both with
and without the four optional fields.

The production posting audit under `internal/` and `cmd/` found no serialization
of a `job.Job` into a Feed post. The Orchestrator's child-job post copies a
previous record body, and `grid feed post` accepts a supplied JSON body. Neither
needs the projection. No new posting command was added.

Run the acceptance checks with the default TMPDIR:

```sh
make test
make lint
GOOS=windows go build ./...
GOOS=darwin go build ./...
go test ./internal/job ./internal/cli -run 'RoundTrip|Record'
```

All checks passed. The full Linux test run reported no temporary-file leaks;
the focused run (with `-v`) showed the new Record and RoundTrip cases. Windows
and macOS were cross-compiled; native runtime tests on those systems were not
available in this Linux environment. No requested implementation work remains.
