## Problem and result

The six-hex approval token could not distinguish two reviewed plans with a
precomputed short-hash collision, and JSON plan-hash output exposed no full
digest. Approval now accepts either six or 64 lowercase hex digits. The short
form compares with `current`; the full form compares with `digest`, inside the
existing `WithDigest` callback. Task-then-plan lock ordering, receipt writes, and
the empty-token reapproval rule are unchanged.

Within task approval, malformed non-empty tokens wrap `task.ErrEditUsage` before
its task resolution, write-lock acquisition, or journal recovery. The existing CLI result mapper
returns exit 2. Valid but stale tokens retain the `plan hash no longer matches`
prefix and exit 1, displaying the current short hash without its full digest.
Both plan and ship receipts always store the current short hash in `plan_hash`
and the current full digest in `plan_digest`, regardless of the token form.
History retains the short `plan_hash` too.

`grid plan hash --json` now returns `hash` and `digest` from the same read,
using unchanged `plan.Hash` and `plan.Digest`. Plain output is unchanged. The
schema permits a 64-lowercase-hex `digest`, keeps `hash` required, and rejects
additional properties. Digest remains optional in the schema so existing
hash-only fixtures and responses still validate.

## Policy and scope

Workflow key: `plan_hash_token: any | digest`, default `any`.
`task.WriteOptions.PlanHashToken` exposes the choice through the options already
passed by the CLI and land approval integration. Empty policy means `any`;
`digest` refuses a supplied six-hex token with `ErrEditUsage` and CLI exit 2.
Unknown policies also fail closed with a usage error. Empty tokens retain the
existing receipt rule under either policy. No workflow file is read to set this
field in this lane; wiring workflow configuration is deferred as requested.
