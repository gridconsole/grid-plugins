# L60: Workflow roles for person and timer gates

## Base and implementation

Started on `lane-L60` at main `7836850`. Main did not contain L55, so the
requested reset to `origin/lane-L55` (`72906d3`) was applied. Main was then
merged to retain L51's `InvalidRecordError` and CLI exit classifier, which
were absent from that L55 branch. No module file was recreated.

`feed.Store.Post` now checks the question's gate kind against workflow policy
using the stamped `Author.Role`, before creating the Feed or opening locks,
tenure files, or spilled bodies. CLI Feed posts, Job posts and MCP `feed_post`
all pass through this check. Holding a Job lease does not grant permission
to post person or timer gates.

Defaults use the existing question schema's role names:

| Gate kind | Allowed roles |
| --- | --- |
| person, timer | cli (the mechanical orchestrator), owner, member, lead |
| ci, job | cli, owner, member, lead, agent, worker |

The question schema remains authoritative about valid question authors;
for example, guest is not currently a question-posting role. Ungated
questions keep their existing rules. Existing Feed records are not rechecked
against present workflow policy when read.

Denied gate posts and gate ID reuse return `feed.InvalidRecordError`, hence
CLI exit 3 and an MCP tool error. The reuse check runs under L55's task-wide
gate lock, before opening or repairing a tenure file. Its read uses an atomic
reader-cache snapshot without updating or creating the reader cache. An
unchanged retry with its original record ID remains idempotent under an
allowing policy.

## Fallback workflow format

L56's workflow reader is not on main. This lane adds a small YAML front-matter
reader for the task-local workflow snapshot at `<task>/workflow.md`, using
the repository's existing YAML dependency. This is an explicit fallback
format, not an implementation of L56's named-template resolution. The
`workflow` name stored in task.md is unchanged.

For example, to allow agents to post person and timer gates:

```yaml
---
name: Release
gate_post_roles:
  person: [cli, owner, member, lead, agent, worker]
  timer: [cli, owner, member, lead, agent, worker]
---
Workflow body.
```

Each supplied list replaces that kind's default. Omitted kinds and a missing
workflow file use defaults; `person: []` denies everyone for that kind.
There is no additional role restriction outside the default and question
schema. Malformed front matter, duplicate mapping keys, unknown gate kinds,
invalid question roles and non-list values reject the gated post before any
write. Workflow policy is read on every post, so edits are not cached.

## Regression evidence

The final CLI squat, MCP squat and CLI reuse tests were copied into a fresh
archive of main `7836850` and run with:

```sh
go test ./internal/cli ./internal/mcp -run 'TestGateSquat|TestGateReuseCLI' -count=1
```

Both packages failed as expected. Main accepted the agent's next-ID timer
through `grid job post` with an acknowledged Job lease, and through
`grid feed post` without that lease. In both CLI cases J-2 had already been
posted with `after: [gate:Q-1]`, and became ready after the attack. Main also
accepted person and timer claims through MCP `feed_post`. The lane rejects
these claims, while explicit workflow overrides admit them.

Current main separately forbids Job-lease writes through `grid feed post`
and MCP; the CLI Feed case clears its lease so it exercises the gate policy
rather than that pre-existing routing refusal. The Job CLI case retains its
valid lease. `TestGateReuseCLI` enables agent timer posts in workflow to
exercise the reuse check and specifically requires exit 3.

`TestGateLockCoversCheckAndAppend` pauses the first writer using the private
per-store `afterGateCheck` hook. While the writer is between the gate check
and append, a second file descriptor must fail a nonblocking exclusive lock
attempt. A competing writer must subsequently receive a final rejection,
leaving one question. No sleep decides the lock assertion. In an isolated
source archive with only the gate-lock acquisition block removed, the test
failed on that exact missing-lock assertion in all 30 runs.

Additional tests cover every default role/kind pair, overrides for every
kind, empty lists revoking person and orchestrator access, malformed policy,
ordinary questions, held/spilled questions and retries, and byte-for-byte
unchanged task trees on refusal (including absent or torn writer files and
large bodies that would otherwise spill).

The acceptance run also exposed an existing main failure in
`TestRecordExitWorkerArgv`: it still expected Job-side records to be accepted
through `grid feed post`. An isolated unmodified-main run reproduced that
failure. The test now checks the existing routing refusal and unchanged
record count; `TestRecordExitJob` retains lifecycle/exit-code coverage on
the supported Job path. Production routing behavior was not changed.

## Validation

All passed on the final implementation:

```sh
go test ./internal/workflow ./internal/feed ./internal/orchestrator ./internal/cli ./internal/mcp \
  -run 'TestGate|TestLegacyDuplicate' -count=30
go test -race -count=1 ./internal/feed ./internal/orchestrator ./internal/cli ./internal/mcp ./internal/workflow
make lint
make test
GOOS=windows go build ./...
GOOS=darwin go build ./...
```

`make test` ran the uncached whole-repository suite and reported no new
temporary-file leaks. Cross-platform checks are compilation evidence, not
runtime test results on Windows or macOS. The main regression and lock-removal
mutation checks above failed as intended. No root DONE.md was added.
