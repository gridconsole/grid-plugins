# L155R: a task folder moved to another project stays held

Branch lane-L155R, on the L155S commits (6b960a4) rebased onto plugin main 91ca0950 (main had moved from 91617acc by the L151 preview commits; no conflict). Code head f564a79e; the final head differs from it by this report only.

## Why
The L155S review (must-fix C4 / G2, probe 3): `StepsFor` took the project from the folder path alone. An agent can `mv` a held task folder under another project whose same-name workflow, or copy of the default, has no plan gate. The guard then read that template, released the task, and Deliver refused it for another reason (`has project alpha, expected beta`), so the two no longer gave one answer.

## Changed
- internal/task/hold.go `StepsFor`: the lookup first checks `inFolderProject`. When the workflow is told through the project (a name, or empty for the workspace default), task.md `project:` must equal the project the folder sits in (an exact match; a case difference fails closed, the safe side). A mismatch is `ErrProjectMismatch`, so `PlanStageWith` reads "unreadable", `PlanHeldWith` holds, the guard denies and Deliver refuses.
  - `PlanHeldWith` checks `ErrProjectMismatch` before its receipt branch and holds: a receipt does not release a moved task. Every other lookup error keeps the receipt behaviour of L155S (unknown name plus a fresh receipt is released, as on main).
  - A Personal task (folder `personal/tasks/...`) may leave `project:` out and reads as before; `project: personal` in that folder reads as before.
  - An inline `workflow: [...]` list needs no project, so it reads as before, in any folder.
  - A project task moved into `personal/tasks`, a Personal task moved into a project, and a task with no `project:` key moved into a project are all mismatches.
- internal/guard/plan.go, the "unreadable" deny: it no longer asks for an inline `{step, kind}` list only. It names a workflow that workflows.md defines for the task's own project (the project in task.md is the one its folder sits in) as well as the inline list.
- Tests only otherwise.

## Goal 3: mB (Deliver drops the caller filter) cannot change a result
Added `TestNamedWorkflowDeliverRoles` (internal/guard/plan_stage_steps_test.go): the five roles of `TestNamedWorkflowRoles` (owner, member, invited guest, signed out, filtered guest) at plan and at build, through the store with that role's caller. The shared table `namedRoles` and `as()` now drive both tests; the store's caller is read once, so `as()` sets it.
- Deliver and the guard agree on all 10 rows. The filtered guest is refused at both steps with `where.ErrTaskNotFound`, before the hold lookup, and the folder is untouched.
- `TestNamedWorkflowFilteredGuestHoldLookup`: the hold lookup alone reads "unreadable" with the filtered caller and "past" without it, so mB would matter if Deliver reached the lookup with such a caller.
- internal/task/hold_test.go `TestDeliverNeverAsksTheHoldForAFilteredCaller`: the same for the other filter the lookup applies (Personal policy): a member and a guest get `ErrTaskNotFound` from Deliver on a Personal task, an owner does not.
- Why equivalent: `Deliver` resolves the task with `s.Show`, which uses `s.Resolver` with the caller, and builds the hold lookup from the same `s.Resolver`. Both filters (guest invitations, Personal policy) refuse the same callers, so the lookup is only reached for a caller it reads the task for. The mutation run confirms it: mB survives, 0 red.
