## What changed

- `internal/routine/launcher.go` (new): `LauncherPath(gridHome)` is `<gridHome>/bin/grid` (`grid.exe` on Windows). `RefreshLauncher(gridHome, exe)`: refuses a relative path or a Grid home that is not a folder (it never creates the Grid home); resolves symlinks in `exe` and leaves the launcher alone when `exe` is the launcher itself (a timer starts the launcher and macOS may report it as the executable, which would link it to itself); Unix: `Readlink` equal to exe means unchanged, else a temp link `grid.<pid>.tmp` in `bin/` renamed over it (`Readlink`, not `Stat`, so a dangling link is replaced); Windows: hard link, falling back to a copy that keeps exe's modification time, replaced only when size or mtime differ. Folder mode 0700.
- `cmd/grid/main.go`: `blLaunchRefresh(env.GridHome)` before `cli.Run`, skipped when the Grid home is empty, `os.Executable` fails, or the executable is under `os.TempDir()` (as named and as resolved); the error is dropped.
- `internal/cli/routine.go` (the `default:` branch before the Scheduler is built, plus the `os` import): `Binary` is the launcher when `os.Stat` finds a regular file there (a dangling link falls back), else the executable as before. `routine run` (the `ProcessExecutor`) is unchanged.
- Tests: `internal/routine/bl_launcher_test.go`, `internal/routine/bl_launcher_unix_test.go` (`!windows`), `internal/cli/bl_launcher_cli_test.go`.

Timers already installed keep their old path until `grid routine schedule` runs once on the new binary; this lane does not walk installed timers.

## NOT VERIFIED

- `cmd/grid/main.go` is covered by the build only: it has no test (a test file there is outside the brief's Touches, and `main` cannot be called from `go test`). The refresh and the TempDir skip in a real binary were not run: the shell cannot start a built binary with `GRID_HOME` set.
- Windows: the hard link and copy logic runs here through `blLaunchFile` on Linux, and Windows builds and test-compiles; it was not run on a Windows machine, nor was a Task Scheduler task started on a hard link. On Windows `os.Rename` onto a launcher that a timer is running fails and the error is dropped; the next run retries.
- macOS: the launchd plist names the launcher in tests; a launchd job starting a symlink, and what `os.Executable` returns then, were not run.
- No real OS timer was installed; the fake `systemctl` and `launchctl` scripts only logged.

## Open items

- Any grid binary outside the temporary folder repoints the launcher at itself: a `make build` binary or a second installed version will take the launcher from the plugin (and back on the plugin's next run), so timers run whichever version ran last. The brief's design accepts this; a note for the owner.
- Between an update and the first grid run on the new version, the launcher dangles and a timer fails to start. Any hook run fixes it.
- The row 3 test reads the unit through fake OS commands on PATH because the CLI has no backend seam; a `Backend` or `Runner` field on `Env` would let it drop the PATH trick (outside this brief's Touches).
- The tests reuse `plistTopLevel` and `schtasksXML` from `timer_golden_test.go`.
- The lane used about 60 tool calls against the brief's "about 50": the extra went on the base-failure proof and the importer list.
