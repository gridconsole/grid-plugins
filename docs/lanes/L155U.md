# L155U: every task carries a workflow digest; deliver reports the code

Base: lane-L155T 39366c9e, rebased onto plugin main 68e6020e (L154 landed in between;
one conflict in docs/delivery.md, both paragraphs kept). Status: BLOCKED on one
question (below); the rest is built and checked.

## What changed

- `internal/workflow/tasksteps.go`: `TaskWorkflow` returns the template a task's
  steps come from (nil for an inline list) with the steps; the template comes back
  even when the steps do not resolve for the task's size. `TaskSteps` keeps its
  signature and wraps it.
- `internal/task/hold.go`: `DefinitionDigest` is the sha256 over the template's
  full step list (per step: lowercase name, kind, plan gate of the full list,
  sizes), in order, whatever the task's size. An inline list digests its own
  steps, each for every size. `StepsFor` compares it as soon as the template is
  found, before the steps resolve, whenever `workflow_digest` is present.
  One form only (plain hex, no `v2:`): nothing with the L155T form shipped, and a
  value of the old form now reads as a change, which holds.
- `internal/task/create.go`: `grid task new` stamps the definition digest for
  every size, `auto` included. No template to find at creation (a name no
  `workflows.md` holds, an unreadable `workflows.md`, an empty `workflow` when
  the rules need a choice or there is no default) still leaves the field out:
  those tasks keep the folder-name check, as today.
- `internal/cli/deliver.go`: a refused `grid deliver` records its error, so
  `--json` prints `{"error":{"code":"workflow_changed","message":"Deliver blocked: ..."}}`
  on stdout; stderr and exit 1 are unchanged. No `plan_not_approved` code exists
  in the contract or `error_codes.go`, so none was added; a plain plan refusal
  keeps no envelope.
- `contract/README.md` (code row, digest paragraph) and `docs/delivery.md`
  name `grid deliver` and describe the definition digest.
- `internal/cli/deliver_workflow_changed_test.go` (new): the review's size-auto
  S1/S2 through the CLI root (`grid task new`, `grid hook pretooluse`,
  `grid deliver --json`), size large S1/S2, renamed back and rebuilt identical,
  and a size-auto task sized later by a person.

## BLOCKED: an inline list on a task stamped from a template

The decision says compare always when the field is present and that an inline
list digests what it has. `TestNamedWorkflowMatchesInline` (L155S,
internal/guard/plan_stage_steps_test.go:55) makes a size-large task from Large
(plan, L-only preview, build), keeps its digest, swaps `workflow: Large` for the
same three steps inline, and wants the same stage. The template's definition
(preview for L only) and the inline one (every step at every size) differ, so
it reads workflow_changed:

```
--- FAIL: TestNamedWorkflowMatchesInline (0.10s)
    plan_stage_steps_test.go:61: step plan: named "gate", inline "unreadable"
    plan_stage_steps_test.go:61: step build: named "past", inline "unreadable"
```

Question: for a task whose `workflow:` is an inline list, should the definition
compare (a) hold it as workflow_changed, and that L155S row change, or (b) be
skipped for inline lists (the list sits in task.md itself), or (c) something
else? Not decided here; the code does (a), literally.
