# L72: Retry gate posts after workflow policy read failures

Base plugin main: `1c70a9c4f57d21b7b129aa33246b10ba506a5f58`.
Branch: `lane-L72`.
Validated implementation head: `91a0d05a17ea5172c5a0f38c6993716c9297cd75`.
Regression tests were committed first in `f2025f1`; this note follows the
validated head in a documentation-only commit. No unlanded lane is required.

`Store.Post` now returns a plain wrapped error when reading gate policy fails
with a `PathError` or `SyscallError`. The CLI therefore returns exit 1 and callers
can retry. Malformed policy still returns `InvalidRecordError` and exit 3.
Missing policy still uses defaults. All policy failures return before Feed
preparation, appending, or reserving a gate ID.

The stray tracked `internal/feed/store.go-e` is deleted. Production changes are
five lines inside the gate policy block in `Post`. Only the five authorized
paths changed; no changes outside the touch list were needed.

## Choices and coverage

- Use `os.PathError`, the alias of `fs.PathError`, to keep the change entirely
  inside the permitted block without adding an import. Both error types are
  matched with `errors.As`; `%w` preserves their causes. The added diagnostic
  prefix is `read gate post policy`.
- Keep the existing parser and its not-exist defaults unchanged. Other policy
  errors retain the fail-closed invalid-record classification; no fallback
  policy is used after a read error or malformed content.
- Use a valid person gate posted by a member in both suites. Check chmod 000,
  a directory named `workflow.md`, malformed YAML, and a missing workflow.
  The store tests also verify `PathError` and permission causes survive wrapping.
  No production fault-injection hook was added for synthetic syscall errors.
- For each policy failure, assert the Feed directory was never created, which
  also proves no line was appended. Repair the policy and post the same gate ID
  again; require exactly one record at sequence 1. The CLI tests run the actual
  command dispatcher with `feed post --type question --body ...`, checking
  exit 1 for read failures, exit 3 for malformed policy, and exit 0 for defaults
  and successful retries.
- Skip chmod rows when running as root because root can read mode 000 files.
  This validation ran as a non-root user on Linux, so neither chmod row skipped.
  On Windows, skip chmod and use the directory row. The directory row also runs
  on Unix, retaining read-failure coverage when running as root.
- The base supports successful Feed writes only on Linux and macOS. On other
  platforms the new tests still check read/malformed failures and absence of
  writes, but omit retry acceptance and skip the missing-policy success row.
  Windows test binaries were compiled, not executed; no native Windows or
  Darwin runtime pass is claimed.
