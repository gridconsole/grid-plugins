## Decisions and safety

- Delete follows the actual Rust ordering, using the exception expressly allowed
  in the brief: rename first, then a `deleted` history receipt. Rename failure
  leaves no delete line, so no compensating line is needed. Restore follows the
  requested plugin ordering: rename first, then `restored`, deliberately differing
  from Rust. Task state, metadata, ULID, intent and payload bytes are preserved.
- The rename is the move's commit point. Receipt failure returns exit 1 with an
  explicit message that the task moved; it never rolls the move back. Receipt
  writes use the existing recoverable task journal. A crash between rename and
  receipt can leave a moved folder without that receipt, as in Rust; there is no
  new move journal or cross-filesystem copy/delete fallback. Existing pending
  task journals are recovered under the task lock before acting.
- The UTC clock provides `YYYYMMDDTHHMM`. An already occupied destination, including
  an empty directory, is refused with exit 3. No suffix is generated. A recreated
  task with the same folder cannot overwrite a same-minute trash copy. Restore
  chooses greatest valid minute stamp, then greatest folder name for ties;
  malformed matching stamps fail closed with exit 2. Other copies stay in trash.
- Restore requires `--project`; delete accepts it as a constraint, otherwise
  resolves a home-wide id. An occupied restore id is refused even with a different
  slug. Unknown delete ids exit 1 like existing task resolution; no trash copy
  exits 3. Duplicate matching delete folders fail closed with exit 3.
- Both moves hold the existing `.task.lock` handle across rename, opened through
  `internal/fslock` with Windows delete sharing. They also use New's existing
  `.task-alloc.lock`, in allocation-then-task order, to serialize restore's
  occupied-id check and publication against creation and other folder moves.
  No new lock namespace or operating-system lock implementation was added.
  Stable lock files can be initialized during checks; refused operations do not
  create trash folders or change task content (apart from prior journal recovery).
- Task lease acquisition now takes the same task lock before opening or creating
  a tenure and verifies the locked inode still exists at that path. This closes
  the absent-lease race and prevents a waiting acquisition from recreating the
  moved task. Lock order is allocation → task → lease for moves and task → lease
  for acquisition. A recorded non-null holder is refused even if apparently stale,
  remote or uncertain; malformed leases are refused too. Restore also refuses a
  recorded holder. The plugin takes or breaks no task lease and ends no sessions.
- Existing path components are checked with `Lstat`, including ancestors of
  absent destinations. Linked trash, projects, project, task or candidate folders
  are refused with exit 2, as are linked task metadata/history files. A linked
  project encountered during discovery also fails closed instead of being skipped.
  File opens use `fslock.OpenNoFollow`. Locks coordinate cooperating writers;
  arbitrary external directory replacement is not a supported concurrency model.
- `DeleteAllowed(role string) bool` and `RestoreAllowed(role string) bool` default
  to exactly `owner`; workflow initialization may replace them for
  `task_delete_roles` and `task_restore_roles`. No workflow file is read. The CLI
  maps an absent role or the ordinary `cli` role to owner, uses `GRID_ACTOR` or
  `local`, and never uses `GRID_WHO` or a flag to claim an identity. Member, guest,
  unknown roles and agent shells are refused with exit 3 by default. The direct
  Store API requires a person identity and explicit role.
- Personal tasks require the caller's explicit person-guard result, derived by
  the CLI from the existing `agentShell` guard, and use `trash/personal/`. Project
  name and id resolution remain available. There is no interactive confirmation.
- An existing history file must be regular and appendable; mode-read-only history
  is refused even under a privileged test process. Missing history is created
  through the existing Go receipt writer, matching other Go task writes and tasks
  created by `New`; this deliberately differs from Rust's existing-file requirement.
  Only task history is written; the extra Rust `trash/deleted.md` log is outside
  the requested contract and was not added.

## App argv

The app supplies its authenticated `GRID_ACTOR` and actual `GRID_ROLE` in the
environment, and ends sessions/tenures before invoking a delete. It must not omit
the role and rely on the ordinary terminal's local-owner default.

- `delete_task`: `["grid", "task", "delete", id, "--project", project, "--json"]`.
- `restore_task`: `["grid", "task", "restore", id, "--project", project, "--json"]`.

Both return `{project, id, folder}`. Delete's folder includes the stamp; restore's
folder is the original task folder name. Plain output is that folder and a newline.

## Exact added contract paragraph

`grid task delete <T-NN> [--project <p>] [--json]` moves the whole task folder to `<GRID_HOME>/trash/<project>/<folder>@YYYYMMDDTHHMM/` using the UTC minute; `grid task restore <T-NN> --project <p> [--json]` restores the newest stamped copy. Both hold the existing task lock and serialize folder publication with task creation, append one history receipt after a successful move, print the resulting folder name, and return `{project, id, folder}` with `--json`. Delete accepts any state but refuses the standing Planner and any recorded task lease holder; it never takes or breaks a lease. Same-minute destination collisions, occupied restore ids, absent trash copies, and denied roles exit 3; unsafe symlink paths and invalid input exit 2; unknown delete ids and I/O failures exit 1. Neither move overwrites an existing folder or copies across filesystems. A failed rename leaves no history receipt; a history failure after rename reports that the move happened and does not undo it. Actor and role come from `GRID_ACTOR` and `GRID_ROLE`, with local-person/owner defaults for an ordinary shell; agent shells are refused, and Personal tasks require the same person guard and use `trash/personal/`. Replaceable `DeleteAllowed` and `RestoreAllowed` policies default to owner only; these commands read no workflow file.
