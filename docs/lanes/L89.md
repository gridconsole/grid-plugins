## Changes

- `plan.Digest` computes full SHA-256 of exactly the canonical bytes behind
  `plan.Hash`; the short hash remains its first six hex digits. Existing heading,
  checkbox, status, evidence, whitespace and dependency canonicalization is
  unchanged and tested for both hashes.
- New plan and ship approvals record `plan_digest` beside `plan_hash` from one
  snapshot under the plan lock. Both locked approval reads and the shared
  publication/guard predicate check the digest whenever present. Empty, null,
  wrong-type and incorrect digests fail closed; only absence permits legacy
  short-hash validation. Implicit reapproval also checks the previous digest.
- A JSON receipt takes precedence over legacy prose acceptance and workflow step
  advancement in the guard, so stale strong approvals cannot be released by an
  old history line. Reapproval after explicit review writes the new digest.
- `task.md` now follows the same host-guard write rule as approval files, including
  with `GRID_PLAN_GUARD=off`. This intentionally protects the whole task record,
  not only workflow edits. File tools protect task roots in projects and Personal;
  shell checks reject named writes and still permit reads.
- Both publication and the guard share the plan-step selection rule: retain
  Rust's `approve` plus name-containing-`plan` rule, and also treat an `approve`
  before the first `run`/`work` as a plan gate. Thus `sign-off` before build holds
  work without reclassifying an ordinary delivery approval after build.
- `contract/README.md` documents the additive receipt field and compatibility.

The brief contains no explicit touch-list enumeration. Supporting changes are
limited to `internal/plan/store.go` for a locked digest snapshot,
`internal/task/write.go` for the receipt field, and `internal/guard/context.go`
for shared gate recognition and JSON receipt precedence, plus regression tests
in the affected packages. The required CLI checks also needed

`testdata/golden/task-approve-json.golden` updated for the additive output field;

## Residual risk

An old short-hash receipt stays weak until it is re-approved. Legacy Rust prose
acceptance also keeps its existing compatibility behavior when no JSON receipt
exists; it is not retroactively upgraded. Rust readers that do not know the new
field cannot enforce it. The heading and explicit `--plan-hash` review token
remain short; the full digest binds the bytes present at approval time, not a
new full-strength compare-and-set token for an earlier UI read.

The digest intentionally excludes the same volatile plan content as the short
hash. The host's shell rule remains textual, like the approval-file rule it
extends; it is not a filesystem sandbox for indirect writes.
