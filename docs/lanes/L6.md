# Lane L6: brain

Built `internal/brain` (notes, stores, topics, search, SessionStart index),
`internal/braincmd` (the `grid brain` command group) and its registration in
`internal/cli`. A note is Markdown with YAML front matter. A level is a folder
with its own `knowledge/` and `brain-proposals/`: the personal (home) level is
`$GRID_HOME`, a project level is `$GRID_HOME/projects/<project>`. Reading a
project also reads the personal level; nothing personal is ever copied into a
project's folder or generated files. Guest and external text is data: a proposal from either tier is
never filed as knowledge. Every file read is a regular file of at most 1 MiB,
symbolic links are refused, and paths stay inside their level through `os.Root`.

Verbs: `show`, `search`, `topics`, `index`, `propose`, `accept` (with
`--reject <why>`), each with `--json`. Check it with `make test` and `make lint`
from the repository root, `go test -race ./internal/brain/...` for the lock, and
`go run ./cmd/grid brain help` for the usage.

## Brain id shape

An id is `brain:<level>/<name>`. Level is `home` or `project`; name is one plain
name (`[A-Za-z0-9][A-Za-z0-9._-]*`, at most 100 characters, no `..`). The topic is
not part of the id: a name is unique within its level across topics (accept
refuses a name another topic already holds), and the note is the file
`knowledge/<topic>/<name>.md`. An unqualified `<name>` means the project note
first, then the personal one. A proposal has the same name without the prefix and
lives at `brain-proposals/<name>.md`. A link target is `brain:<level>/<name>`,
`job:<task>/<job>` or `person:<id>`, each optionally followed by `#anchor`.

Lane L14 is reworked to use this shape. It must not use
`brain:<level>/<topic>/<name>` or read note files itself; it resolves an id with
`Store.Show` and checks a link with `Link.Validate`.

Other files a level holds: `knowledge/index.md` and `knowledge/backlinks.json`
(a numeric `generation`), both generated by `grid brain index`;
`knowledge/log.md`, one line per keeper decision; and `.brain.lock`.

## Changes made at merge

- The write lock is `fslock.LockExclusive` (L7's shared flock) on `.brain.lock`
  in the level's folder. A second writer blocks until the first finishes; the
  kernel drops the lock when the holder exits, so a killed writer cannot wedge the
  brain, a leftover `.brain.lock` file holds nothing, and two writers proposing at
  once both land. The wait has no time limit, so a writer that is stopped but not
  dead holds everyone up. The file stays in place after a write; removing it would
  let two writers lock different files. Where `fslock` has no implementation
  (Windows) a write returns its not-supported error and reads still work; the
  tests that start child processes need macOS or Linux.
- Tiers are `contract.TrustTier` and its constants, not strings of the lane's own.
- Front matter is read and written with `go.yaml.in/yaml/v4`. The hand-written
  parser and emitter are gone. Parsing refuses unknown fields, duplicate keys,
  anchors, aliases and explicit tags. The emitter escapes control characters, so
  every note the validator accepts reads back.

## Intended differences from the old plugin and the spec

| Difference | Reference and reason |
| --- | --- |
| The verbs are `show`, `search`, `topics`, `index`, `propose`, `accept`, not `query`, `topic <t>`, `check`, `keep`. | `docs/plugin-design.md:476-489` names the spec verbs; the lane shipped the verbs that read and write one level at a time. Align the names or the spec in the app lane. |
| The eight built-in topics are a list in Go, not read from the plugin's `topics/<topic>/TOPIC.md`. Custom knowledge topics are read from a project's own `TOPIC.md`. | `docs/brain-feed.md:244` makes the plugin files the source; the repository's `topics/` holds only a README, so the Go list is the only copy until those files exist. |
| A proposal from a guest or an external source is recorded as `rejected`, a final state. | `docs/job-contract.md:91` lets a team member's source line promote it, and `docs/brain-feed.md:15`, `:311` (check 9, `:366`) file the old-notes backlog at tier external. A quarantined state a team member can accept is still to build. |
| The secret check matches key names such as `token: ...`, so a note that only names a key can be rejected. | `docs/brain-feed.md:268` asks for notes that name the variable. It should match values (known prefixes, high entropy). |
| Plain output escapes only backslash, newline and carriage return. | Other control characters, including ESC, reach the terminal. Escape all C0 and C1 controls. |
| The SessionStart banner says `grid brain topics lists them`. | The spec names `grid brain topic <t>` (`docs/job-contract.md:96`, `docs/brain-feed.md:282`). |
| A custom topic's description goes into the SessionStart text cut to 80 characters, unfenced. | Any writer of the project brain controls it. It is untrusted text in the session start. |
| A note without `origin` is counted invalid, which is every note from the old plugin. | The migrate lane (L9) must stamp an origin, or the scan must accept a missing origin as external. |
| The directory is not synced after a file is renamed into place. | `atomicWrite` syncs the file only; a power loss can drop the rename. |

## Not covered here

- The lane has no sync: the personal level reaching that person's other computers,
  and the project level reaching its members, belong to the app and server.
- No Windows support for writes (see above); `GOOS=windows go build ./...` passes.
- The authenticated tiers `person-team` and `person-guest` are claimed only by the
  server integration. The command line stamps `agent`, or `external` for
  `--external`, whatever the note text says.

## Left as they are after review

The rows above marked as still to build are the review's should-fix list:
quarantined state for guest and external proposals, value-based secret matching,
control-character escaping, the banner wording, topics from the plugin's own
files, the description cap and fence, the missing-origin scan, and the directory
sync. None changes the id shape or the file layout.
