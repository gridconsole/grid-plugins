# L35 delivery, history add and proof

Reworked after review onto main's task writer (`internal/task/write.go`). The
first branch added a second history writer and a second `task.md` writer; both
are gone. Built and committed without recreating go.mod:

- `grid deliver` imports explicitly listed deliverables through the existing
  artifact store, rebuilds the proof index, then writes the Outcome, the ship
  gate and one delivery receipt in a single `commitWrite` under `.task.lock`. The
  state moves through `NextState`, and the header keeps its key order and
  comments. Pending proposals and insufficient proof refuse with one stderr line.
  Dry runs are read-only.
- `grid brain keep` lists task, project, and home proposals with their topic and
  reason, in plain text or JSON, without making keeper decisions.
- `grid proof add` stores evidence and checksummed metadata per existing plan
  item. `grid proof index` rebuilds a deterministic Result projection. Proof
  is bound to the existing plan hash and verified from the original files.
- `grid history add` calls `Store.Note`, a history-only write through the task
  writer's lock and journal, so it cannot race `task status`. A one-file journal
  (history only) is now complete for recovery.
- `grid approve` after delivery records a ship approval (`approval-ship.json`),
  not a plan approval.
- Item ids (`1`, `i-1`, `item-1`) are parsed by `plan.ItemID`; `internal/proof`
  uses `plan.Items` and `plan.Hash` and parses nothing itself. The `proof:` item
  key is documented in `docs/plan.md` as provisional, for the owner to confirm.
- Waiting proposals at project and home level are read with `brain.Parse`.
  Home-level ones block delivery only when they name this task or project.
- Extended the existing localdata lock entry point to work in task directories
  without creating a Grid home marker. Reused fslock, atomicfile, task lookup,
  the plan parser/hash, brain proposal locks, and the shared frontmatter parser.
  cli.go only registers command handlers and descriptions. No Feed records or
  competing task-record structs were added.

Command usage, formats, proof levels, scope selection, and recovery limits are
in [docs/delivery.md](docs/delivery.md).

## Validation

All of these passed on Linux, using the default TMPDIR:

```sh
make test
make lint
go test -race ./internal/task ./internal/proof ./internal/brain ./internal/braincmd ./internal/cli
GOOS=windows go build ./...
GOOS=darwin go build ./...
```

Tests cover each command and refusals, waiting and malformed proposals, proof
levels and unknown items, missing and tampered evidence, stale plan hashes,
stable index bytes, preservation of Outcome's peer sections and source files,
read-only dry runs, and two separate processes concurrently running history
add without losing or duplicating lines. Race tests include those subprocesses.
The macOS build passed; native macOS execution was not available here.

## Limits and work outside this lane

The four requested command groups are implemented. The broader keeper agent,
`keep --history`, scheduling, dedupe, and closed-Job digests were not built:
this lane requests a read-only keep command, and existing brain decision commands
remain responsible for writes. Task-local legacy proposals are listed and block
delivery; this lane does not migrate them into the existing brain store.

The ship gate is the task.md waiting state and ship marker described above.
`grid approve` records a ship approval for it; nothing yet reads that file, so
landing and closing still need their own commands.
Publishing a Feed approval request, approving, landing, and closing remain with
their own commands; no synthetic Feed approval or alternate contract was added.
The Result and History data are ready for readers; changing the supplied
read-only prototype or building its renderer was outside the request.

The task record, gate and receipt are one commit; artifacts and the proof index
are written before it. A late disk error can leave partial delivery material
without newly raising the gate. Proof verifies
evidence presence, kind, plan binding, and integrity, not whether its content
proves the claimed behavior. Windows builds compile and retain fslock's existing
runtime refusal; implementing Windows locking was outside this lane and the
fslock package was protected from edits.
