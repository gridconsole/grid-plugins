## Guard inputs and compatibility

The SHA-256 input starts with the exact stored `run`, one NUL byte, and the exact
stored `every`. With no entry limit keys and default workflow limits, this is
still the entire input. For `run: grid version` and `every: 1h`, the pinned base
hash is:

```text
a0b16821620a7c0a8f9bf3fd44d3890514df8094797106e4b3b316f6f6132ab9
```

If the entry supplies **any** of `routine_timeout`, `routine_max_turns`, or
`routine_budget` (including an explicit default), or workflow policy supplies a
non-default limit, append these bytes in this fixed order:

```text
NUL + limits-v1 + NUL + timeout_nanoseconds + NUL + maximum_turns + NUL + budget
```

The values are the resolved effective limits: entry key first, same-scope
workflow key second, built-in table default last. Timeout is a base-10 integer
number of nanoseconds, turns a base-10 integer, and budget uses Go
`strconv.FormatFloat(value, 'f', -1, 64)`. There is no final NUL. Thus equivalent
spellings such as `10m`/`600s` and `1`/`1.00` agree. The extended hash for explicit
`10m`, `10`, `1` defaults is pinned to
`973c78f1ca566fe32bfb1a02e7cb1c239eb841a3025635883c827b3e4b93ca14`.

Name, machine, last-run timestamp, outcome, notes, unrelated workflow keys, and
the cached JSON display object are not fingerprint inputs. Existing schedule
identity and machine ownership checks still apply. Workflow defaults fully
masked by entry overrides do not alter the effective hash. Explicit workflow
keys equal to built-in defaults alone retain the legacy hash.

Schedule and timer execution both resolve and validate policy before hashing.
A changed hash returns the existing `ErrScheduleChanged` refusal, before updating
run state or applying the due-interval skip. Repeated refusals leave `last_run`
and outcome unchanged. Running `grid routine schedule` approves the new hash;
unchanged timer files need no OS registration calls. Manual runs remain explicit
requests. Old timers with no limit keys and no non-default workflow policy keep
working; timers approved before this change with explicit limits need approval
once because their old hash did not cover those limits.

## Small missing piece and scope

L120 has only entry policy and built-in defaults; it has no routine workflow
reader. `internal/routine/workflow.go` adds the smallest read-only source needed
for workflow defaults: optional `workflow.md` front matter in the Grid home for
home routines, or `projects/<name>/workflow.md` for project routines. The three
keys have the same types and bounds as entry keys. Projects never fall back to
home policy, matching the existing routine scope rule. This does not replace
routine entries, task-local workflow readers, workflow template endpoints, or
any existing data source.

The new reader uses the existing bounded, root-confined, symlink-refusing file
reader and strict front matter syntax parser. It accepts unrelated workflow
fields without rewriting them. Missing files mean built-in defaults; malformed,
unreadable, nonregular, oversized, or symlinked policy files refuse execution.
Invalid workflow limits are validated even when an entry would override them.
Errors do not echo supplied values or filesystem paths.

An unexported policy snapshot travels with the entry from the guarded read into
the existing executor. A workflow edit after the guard cannot raise that run's
limits. Saving run state never persists inherited keys or rewrites workflow
policy. JSON retains every existing field and reports all effective limits.
`Fingerprint` now returns validation errors to its internal callers instead of
hashing invalid policy. Scheduler changes propagate those errors.

`LimitError` now optionally carries the routine name. `Store.List` preserves it
through the CLI's typed-error formatting, producing, for example,
`grid: routine daily: invalid routine_budget` with exit 2. It includes neither
the bad value nor a path. The supporting reader, tests, and README explanation
are the necessary additions beyond the original hash and error changes;
`go.mod`, generated files, and OS timer definitions are unchanged.

## Base regression and mutation evidence


The legacy hash test passed. All three entry-limit changes and all three
workflow-limit changes failed in both home and project scopes because work ran
again: `changed limit ran: err=<nil>, runs=2; want schedule refusal and runs=1`.
