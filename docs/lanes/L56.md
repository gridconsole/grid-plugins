## Behavior and answer

`workflow.Parse(text, project)` returns successful templates and diagnostics;
empty project means workspace. `workflow.Read(home, project)` reads the shared
file and registered project files, resolving a selection by name or ID through
`gridhome.Real` and `projects.Store.List`. Missing or ambiguous selections fail.
The shared file comes first, followed by projects in registry order. An absent
file remains in the answer with null revision and empty text. Reading creates
no directories, records, or locks. Task workflow selection is unchanged.

The JSON answer has exactly three arrays: `files`, `templates`, and `errors`.
The field definitions are in the ready-to-paste contract block below. A broken
section is omitted; later valid sections still load. Whole-file and section
problems retain Rust's ordering, line numbering, and parser diagnostic wording.
Plain output lists each file label, its template names, and its error count.

Revisions now match Rust: the first **12 lowercase hex characters** of SHA-256
of the exact file bytes, with no newline normalization. This corrects L56's
full-length hash. Reads keep at most 32 KiB of usable text; larger files are
streamed through the hash and reported as errors. Invalid UTF-8 and oversized
files retain their revision and have empty text, matching Rust. Absent files
are not parsed; a present empty file has a revision and a heading error.

The existing reader confines opens through `os.Root`, rejects symlinks below
the resolved home through `localdata.Safe`, and checks regular-file status and
file identity before reading. A symlink spelling of the home itself is allowed.
Read failures remain attached to their file rather than hiding other files.

## Paths and behavior differences

The old plugin's `skills/execute/SKILL.md:138` names
`<projects folder>/workflows.md` and
`<projects folder>/<project>/workflows.md`; its
`evals/execute-review-changes-rework/fixture.sh:15-27` writes a project file.
The supplied spec has no literal `workflows.md` occurrence.
`docs/plugin-design.md:135-137` establishes project records under
`<home>/projects/<name>` and one Grid home without workspaces.
`docs/brain-feed.md:244-248` places workflows configuration at home and project
levels. These agree on shared and project levels, but do not specify the same
absolute layout. Following the spec, the reader uses:

- `<home>/workflows.md`
- `<home>/projects/<name>/workflows.md`

This remains an interpretation of the spec, not a claim that it names these
Markdown paths. No old projects-root fallback is searched. Logical file labels
in templates/errors remain `workflows.md` and `<name>/workflows.md` as in Rust.

Differences and boundaries relative to Rust:

- `workflows.rs:1047-1096` discovers immediate root subdirectories and selects
  a folder by name. Go uses the project registry under the new home layout and
  accepts a project name or ID. Missing/ambiguous selectors are CLI failures.
- `workflows.rs:1057-1060` omits absent project files in desktop all-project
  reads. The brief explicitly requires all registered projects to remain in
  `files`, including absent ones with null revisions. Selected-project reads
  keep both entries, as Rust's hosted read does at `1067-1073`.
- `workflows.rs:368,692,784` uses Rust full/contextual Unicode lowercase. Go's
  standard-library simple lowercase is used for names and handles. For example,
  section names `İ` and `i` collide in Go but not Rust, while `ΟΣ` and `ος`
  collide in Rust but not Go. The same distinction applies to duplicate step
  names. ASCII names, including every supplied inline test, match. Unicode
  table versions also follow the respective toolchains.
- `workflows.rs:1107-1130` uses Rust's errno descriptions and generic non-file
  messages. Existing Go safe-path/I/O errors retain Go wording and may include
  paths; parser wording, NUL, invalid UTF-8 and size diagnostics match Rust.
- `workflows.rs:1169-1187` uses its platform plain-open helper. Go keeps the
  existing `localdata.Safe`, `os.Root` and before/opened/after identity checks.
  A disappearing file during open is reported as a Go I/O problem, whereas
  Rust treats open-time not-found as absent. A disappearance during the final
  Go lstat is likewise a problem; Rust has no final path lstat. Neither is a
  transactional snapshot of concurrent edits to a file's contents.
- Rust uses `Option<&str>` for parser project scope; Go uses empty string for
  workspace. An explicitly empty project name is not a valid CLI selection.
- Read/parse problems are data and do not change a successfully emitted CLI
  response's exit status (0). Selection/home/I/O setup errors use `exitCode`
  (currently 1), usage errors use 2. Main has no distinct not-found constant or
  named numeric exit constants; this lane adds none. Rust's HTTP status/error
  types at `workflows.rs:277-315` do not apply to CLI exit status.
- Go structs are response shapes; they do not enforce Rust's required-rev
  deserialization at `workflows.rs:70-72`. No input/write API is exposed.

Task workflow selection remains unchanged, including empty workflow values on
old task records. Parser parity does not imply porting Rust's task-copy format:
this repository continues to store a template name for a task's workflow.

## Contract README entry to paste in the contract lane

```markdown
### `grid workflow show [--project <name-or-id>] [--json]`

Reads workflow templates without writing. JSON returns `{files, templates,
errors}`; each collection is an array, including when empty.

`files` entries have `scope` (`workspace` or `project`), `project` (folder name
or null for workspace), `rev` (the first 12 lowercase hex characters of SHA-256
of the exact bytes, or null when absent/unreadable), and `text`. Oversized and
invalid UTF-8 files retain their content revision but have empty text. Each
file is limited to 32768 bytes of usable text. The shared file is first; all
registered project files follow, or only the selected project's file when
`--project` is given. Missing files remain with null rev and empty text.

Each template has `name`, `default`, `applies` (rules `{by, v}`, where `by` is
`goal`, `title`, `project`, or `label`), `only`, `approvers`, `repeat`, `lead`,
`batch`, `rounds` (1, 2, 3, or 5), `research`, `steps`, `overrides`, `file`,
`usedIn`, and `openTasks`. Optional scalar values are null; `applies` and
`approvers` are arrays. `usedIn` and `openTasks` are currently empty arrays.

Steps have `name`, `kind` (`check`, `ask`, `approve`, `make-together`, `run`,
`schedule`), `approver`, `approvers`, `agent`, `runs`, `sizes`, and `back`.
Optional values are null; an approve step has a one-item `approvers` array.
`sizes` contains selected letters in S/N/L order (`SNL` means all). The legacy
agent name `grid-worker` reads as `grid-builder`.

Errors have `file`, `section` (null for a file problem), `line` (1-based or
null), and `message`. A bad section is omitted from `templates`; the rest of
the file and other files still load. File labels are `workflows.md` or
`<project>/workflows.md`. The physical locations are `<home>/workflows.md`
and `<home>/projects/<project>/workflows.md`.

Plain output lists each file label, its template names, and its error count.
A successfully emitted response exits 0 even when it reports file/section
problems. Unknown or ambiguous projects and unavailable home resolution exit
1; invalid command syntax exits 2. Duplicate names use Go's simple Unicode
lowercase comparison; see the lane notes for its non-ASCII Rust differences.
```
