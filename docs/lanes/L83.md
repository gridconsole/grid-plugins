- `internal/task/write.go:285-291` marshals that same event and appends it to

  ```go

  ```
  History is an audit trail, not publication authority. Neither a legacy
  `plan accepted` prose line nor a JSON history bullet replaces the current
  receipt. `internal/task/history.go:127-129` also quotes approval-like detail
  text (`"plan accepted", "preview approved", "ship approved"`).
- `internal/task/gates.go:147` checks the receipt against the actual plan:
  ```go
  if event.Task != t.ID || event.What != "approve" || event.PlanHash != hash {
  ```
  Closed tasks, missing receipts and malformed receipts are also rejected.
  `ApprovalForGate` already checked `event.Gate != eventGate` at lines 100-101;
  the lock-free `Approved` predicate omitted that check. It now requires the
  empty gate used by plan receipts, rejecting ship and unknown gates.

Feed approval uses `question`, `answer` and `control` records for question
gates. `internal/contract/types.go:161-162` says:

> Question is a counted question with its answer candidates. Only a task
> control that selects one of them closes it; arrival order never does.

`contract/README.md:193-195` specifies:

> Closing a question selects
> `{target: question-post-id, answer: answer-post-id, status: answered|closed}`;
> neither of two concurrent answers wins by time.

These question controls do not carry a plan hash. There is no plan-approval
Feed post type to consume instead of the receipt. The `post` kind enumeration
in `contract/schemas/post.json:46-54` is `message`, `pickup`, `ask-pickup`,
`ship`, `close`, `reopen`; a ship post is not plan approval. Publication keeps
using the existing revision-bound receipt rather than interpreting free text
or an unrelated closed question as approval.

## Workflow decision and publication behavior

Reuse L43G's `taskfile.PlanApprovalRequired`. Its own source documents the
default at `internal/taskfile/workflow.go:42-43`:

> PlanApprovalRequired reads the inline workflow used by existing task guards.
> Missing, unresolved named or malformed workflows require plan approval.

Lines 51-55 recognize `run`/`work` and require approval for an `approve` step
whose name contains `plan`:

```go
case "run", "work":
case "approve":
    if strings.Contains(step.Step, "plan") {
        return true
    }
```

The function returns false for a valid explicit workflow without a plan gate;
unknown kinds and invalid or duplicate steps require approval. This preserves
the workflow's ability to omit approval rather than imposing approval on
every plan.

There is a naming distinction in this base: plan step policy is the inline
`workflow` in `task.md`, as read by `publishPlan` at lines 48-52. Task-local
`workflow.md` currently supplies Feed gate role policy, not a plan-step gate
field. `internal/workflow/gates.go:16-20` says:

> GatePostRoles reads gate_post_roles from the task's workflow.md front matter.
> Omitted kinds retain their defaults; a supplied list replaces a default, and
> an empty list forbids that kind. Policy never expands the question schema's
> set of author roles. The withdraw action uses the control schema instead.
> Missing workflow files preserve older tasks' defaults.

`WorkflowStep` has only `Step` and `Kind` (`internal/taskfile/workflow.go:10-13`).
Retaining the explicitly permitted L43G heuristic avoids inventing a new
workflow field or a second resolver in this security fix. Its known limitation
remains: a plan approval step must include `plan` in its name; unresolved named
workflows require approval.

When required approval is absent or invalid, publication adds no Feed records,
returns nil, and emits exactly one standard logger line per attempt:

```text
plan publication skipped: workflow requires approval of the current plan
```

The logger writes to stderr by default. It does not put a diagnostic in the
Feed or change the tick's success status. Approved and waived publication emit
no such line. The existing `.task.lock` then `.plan.lock` ordering still covers
approval checking and publication, preventing cooperative edits or approval
replacement between the check and Job posting. Existing published Jobs retain
their lifecycle.

Revision matching retains `plan.Hash`, the same hash used by `grid approve`.
`internal/plan/hash.go:25-27` documents its compatibility semantics:

> Hash is byte-compatible with plan-hash.mjs: six hex digits of SHA-256.
> The first line is always omitted, even on a plan without a revision heading.
> Internal blank lines, leading indentation and spaces within text still count.

Thus an intent edit such as changing a planned Job's role requires reapproval.
Existing normalization of progress checkboxes, evidence and the heading is
unchanged; this is the existing short semantic hash, not a new full-byte digest.
