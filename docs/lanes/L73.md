# L73: Personal settings access and private task path errors

Plugin main inspected: `1c70a9c4f57d21b7b129aa33246b10ba506a5f58`.
It did not contain `internal/cli/personal_bypass_test.go`, so the requested
fetch, reset to L67R (`f7375188126af8acdb3e21b269f813535715e1ba`) and rebase
onto main were performed. The resulting L73 implementation base was `483bc62`.
Code and test validation head: `a71ed443b8a84e217736f2d9ace90905c468f572`.

## Changes

`settingsStore` now resolves an omitted write project as explicit `personal`
before returning a Store. Default and explicit Personal writes therefore have
the same exit status and stderr for refused callers, even from a registered
project. Hook levels, skill enable/disable, agent settings and setup all use
this adapter. Refusal happens before any settings, lock, version or setup file
is created. Reads from an unregistered folder also resolve their Personal
fallback. Registered projects retain their existing effective-settings
inheritance.

The brief's unknown-role refusal requirement differs from L67R, which allowed
all unknown roles through `contract.TierFor`'s agent fallback. This lane follows
the new explicit requirement in the shared Personal policy, rather than adding
a different settings-only policy. Unknown roles are now refused for all Personal
access. Owners, empty roles, cli/host/worker/agent sessions and every current
plugin agent retain access. Plugin agent names work both with and without the
`grid-` prefix. Existing member/lead identity rules and the replaceable
`PersonalAllowed` callback are unchanged. The two existing unknown-role
allowance assertions now assert refusal; the existing task attachment test
continues to pass unchanged with `GRID_ROLE=grid-builder`.

For MF3.10, this lane chooses the permitted path-free error: any explicit path
inside Grid home that does not identify a task folder returns `task not found`.
This removes both absolute paths on every platform without assuming that all
Darwin volumes are case-insensitive or changing project-name matching. Canonical
Personal paths still use L67R's early refusal; case variants that fail task
parsing now receive the same text. The existing invalid-internal-path assertion
was updated to the new message, including for allowed callers.

Production changes are limited to `internal/cli/settings.go`,
`internal/where/where.go` and `internal/where/personal.go`. The policy edit is the
smallest additional change needed to reconcile the unknown-role requirement
with L67R. Tests and this note are the other changes; no module file, Makefile,
golden fixture or root DONE file was changed.

## Regression evidence

The new tests were copied unchanged into a disposable archive of main at the
SHA above. These groups failed as expected:

- `TestSettingsPersonalWritesRefused`: guest and unknown-role hook/skill writes
  succeed and change seeded settings bytes; agent writes are covered too.
- `TestSettingsPersonalReadsRefused`: Personal and unregistered-folder reads
  succeed for callers that must be refused.
- `TestSettingsRefusalCreatesNothing`: missing settings and setup files are
  created by refused callers.
- `TestPersonalInvalidTaskPathIsPrivate`: `where --task` and `feed read --task`
  disclose paths for mixed/upper-case Personal roots and invalid internal paths.
- `TestSettingsStoreChokePoint`: default-write and Personal read-fallback
  branches return a Store without access resolution.

The initial regression run on the rebased L67R implementation also failed for
the settings bypass, unknown-role allowance and case-variant path messages.
The final lane tests cover seeded byte preservation, absence of new files,
allowed callers, project read inheritance, existing and missing tasks, and both
CLI path consumers. `TestPersonalCaseVariantTaskPathDarwin` repeats the case
variants under a Darwin runtime guard. This Linux validation skips that guarded
test; the same path cases pass in the portable test. No native macOS execution
is claimed.

The choke test parses Go imports and declarations: production references to
`settings.Store` must stay inside the shared `settingsStore` adapter, including
when the import is renamed. Behavioral checks exercise the adapter's default
write and read-fallback branches. An injected scratch writer using a renamed
settings import failed the choke test as expected; the scratch file was removed.
