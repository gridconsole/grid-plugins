# L43: task lease commands

The existing `grid lease` command now accepts `task` for take, release and status. Merge lease behavior is unchanged. Task commands use the existing Feed resolver and writer identity, so the task must already have a stable ULID in `task.md` (`id` or `ulid`).

```text
grid lease take task --task T-07 --project example --pid <pid> --pid-start <RFC3339>
grid lease take task --task T-07 --project example --session <session-id>
grid lease status task --task T-07 --project example --json
grid lease release task --task T-07 --project example --epoch 0.1
```

Task and project flags are optional when the current task resolves. Take requires an explicit process identity or a registered local session. It never defaults to the parent shell's pid. Handwritten start times must be RFC3339; storage uses UTC, milliseconds and `Z`. Legacy session process tokens are converted only after proving that the recorded process identity is still alive. `session.ProcessStart` runs `ps` with `LC_ALL=C` and `TZ=UTC`; its timestamp round-trips through `ProbeLocal` at second precision.

Successful take prints:

```text
task lease taken, fence 1
epoch 0.1
```

The epoch is passed to subsequent Feed and Orchestrator commands as `--lease-epoch`. Take JSON contains `lease`, `holder`, `gen`, `fence`, `since` and `adopted` (null or `session-gone`). Release requires the exact holder, generation and fence. Status includes holder, generation, fence, since, pid and process state: `alive`, `dead`, `unknown`, or `remote`. A free lease prints `task lease free`.

## Grant, adoption and recovery

`TaskStore.AdoptTask` checks the old holder's machine and probes its pid/start pair while holding the task lease's exclusive lock. Only `Dead` permits adoption. Live, unknown and remote holders remain held. The existing tenure-end log and shared fence counter are reused, and the current generation is preserved by the CLI.

A new task holder posts `handover` as its first Feed record. Adoption includes `adopted: session-gone` and `from`. `old_fence` is omitted because `contract/schemas/handover.json:30-63` does not allow it. The old fence remains in the takeover log.

`feed/lease/task-take.lock`, opened and locked through `internal/fslock`, serializes CLI takes through their handover posts. This prevents a concurrent taker from mistaking an in-progress grant for a failed handover. Its contents retain the granted fence and handover body as retry metadata; this file grants no authority. The lease owner still validates and probes under the lease file's own exclusive lock. Neither lock file is replaced or removed.

If handover fails after a grant, take prints the grant and error, exits 1, and retains the lease. A same-holder retry consults the Feed: if that tenure has no counted handover, it posts the missing record without advancing the fence. Completed handovers cause subsequent live-holder takes to be refused.

All listed commands passed on Linux. Tests cover contract validation, a live real process, a reaped child's identity, remote and unknown refusals, takeover snapshots, exact-epoch release, local/remote status, session resolution, handover failure and retry, and concurrent takers in two goroutines and two re-executed test processes. A store test verifies that release cannot pass the adoption probe while it holds the lease lock.

The reachability test creates a task and writes a checklist plan with one Job. It explicitly supplies a stable ULID fixture, takes the task lease through the CLI, checks that `job next` passes its lease check, publishes the Job through `grid feed post`, then observes the assigned J-1 row using the printed epoch. This is not the exact four-command acceptance sequence; see the prerequisites below.

## Remaining integration prerequisites

- `task new` currently writes only the display ID (`internal/task/create.go:76-110`). The shared Feed resolver requires a stable ULID (`internal/cli/feed.go:190`, `internal/feed/identity.go:54`). Fresh tasks therefore cannot take a task lease without that metadata. Task creation is outside this lane's listed files; no second task metadata writer was added.
- `plan write` stores the plan without publishing Feed Jobs (`internal/cli/plan.go:100-118`). The Orchestrator loads Jobs exclusively from Feed (`internal/orchestrator/ready.go:29-58`). Returning a ready Job from the exact requested sequence still needs that integration. Orchestrator and Job code were left unchanged.
- Windows cross-compiles and take refuses with `task lease needs a Unix host for process identity`. However, runtime status of an existing lease and release remain blocked by the existing Windows `fslock` stubs (`internal/fslock/fslock_windows.go:7-12`). Those return `ErrUnsupported`; the protected package was not changed and no alternate lock implementation was introduced.

Spec decisions and differences from the old plugin are recorded in `DONE.md`.
