# L146: eval check types that read the agent's trace

Base: main at 03a9e574 (298aee0f or newer). Branch: lane-L146. Packages: `internal/eval` only.

## What changed
- `internal/eval/trace.go` (new): `ToolCall`, `TraceParser`, `DefaultTraceParser` (policy key `eval_trace_format`, default `claude-stream-json`), `ErrNoTrace`, the `tool_used` and `tool_order` evaluation, and the capped trace file writer.
- `suite.go`: `Check` gained `tool`, `input_contains`, `count_min`, `absent`, `before`, `after` (all `omitempty`, so existing result JSON and `SchemaVersion` are unchanged); `Validate` checks the two new types at load, naming the check id.
- `check.go`: `evaluate` takes the trace input; the existing types ignore it.
- `process.go`: `RunProcess` is unchanged for callers; an internal `runProcess` can copy the full stdout to a second writer. `ProcessResult.Stdout` keeps its 64 KiB cap.
- `runner.go`: `Runner.TraceParser` (nil = default) and `Runner.TraceLimit` (policy key `eval_trace_stdout_limit`, 0 = `DefaultTraceLimit`, 64 MiB). The agent's full stdout goes to `<attempt>/trace.jsonl`, a sibling of the workspace, up to the limit; past it the file is cut and marked truncated. The attempt folder is removed with the rest of the attempt.

Behaviours to know:
- "Truncated" means the trace file hit `TraceLimit`, not `ProcessResult.Truncated` (that one is set whenever stdout or stderr passes 64 KiB, which every real stream-json run does).
- A stdout with no JSON-object line is `error` "no trace", also for `absent: true`. A stdout with JSON lines but no tool call is a real, empty trace.
- The fake agent prints no trace, so a trace check under the fake agent is `error` "no trace".
- Trace checks score as `code`; they are skipped like all checks when setup or the agent did not succeed.
- Tool calls are numbered from 0 in the order they appear (`ToolCall.Index`).

## Check-type reference

### tool_used
| Field | Required | Meaning |
|---|---|---|
| `tool` | yes | exact tool name |
| `input_contains` | no | object of input field -> substring; all must match; string fields only, substrings nonempty |
| `count_min` | no | calls needed, default 1; not with `absent` |
| `absent` | no | `true` passes when no call matches |

### tool_order
`before` and `after`, each `{tool, input_contains}` with the same rules. Passes when the first call matching `before` comes strictly before the first call matching `after`, and both exist. It takes no other field.

### Mapping the unmapped graders (L139)
```json
{"id":"skill-fired","type":"tool_used","tool":"Skill","input_contains":{"skill":"execute"}}
{"id":"reviewer-started","type":"tool_used","tool":"Agent","input_contains":{"subagent_type":"reviewer"}}
{"id":"reviewer-before-waiting","type":"tool_order",
 "before":{"tool":"Agent","input_contains":{"subagent_type":"reviewer"}},
 "after":{"tool":"Edit","input_contains":{"new_string":"status: waiting"}}}
{"id":"no-shell-edit","type":"tool_used","tool":"Bash","input_contains":{"command":"sed -i"},"absent":true}
{"id":"used-grid-home","type":"tool_used","tool":"Bash","input_contains":{"command":"GRID_HOME"}}
```
Notes for the case lanes: `skill-fired` matches the skill name as a substring (`grid:execute` contains `execute`). `no-shell-edit` needs one absent check per write pattern the skill owns (`sed -i`, `>`, `tee`); a Write or Edit tool call on the owned file is `tool_used` with `tool` `Write` or `Edit`, `input_contains` `{"file_path":"<name>"}` and `absent: true`. `used-grid-home` matches the command text; reading the value from the environment shows as `$GRID_HOME` in a command, so use the substring `GRID_HOME`. The exact input field names (`subagent_type`, `skill`, `command`, `file_path`, `new_string`) are those of the Claude Code tools; confirm them against a real trace before mapping a case.
