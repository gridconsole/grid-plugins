## What changed

- `internal/proctree/proctree.go` (new): `Run(cmd *exec.Cmd) error`, built on an unexported `ops{start, attach, wait, end}` and `run(ops)`. `end` runs (deferred) only if attach returned no error and a non-zero handle; an attach failure is never the run's error; the error returned is Start's or Wait's, unchanged.
- `internal/proctree/proctree_windows.go` (new): `CreateJobObjectW`, `SetInformationJobObject` (extended limit information, KILL_ON_JOB_CLOSE only), `OpenProcess(PROCESS_SET_QUOTA|PROCESS_TERMINATE)` on `cmd.Process.Pid` right after Start (os/exec still holds its own handle until Wait, so the pid cannot have been reused), `AssignProcessToJobObject`; after Wait, `TerminateJobObject` and `CloseHandle`. If the struct size is not 144 (a 32-bit build) attach returns an error and the command runs as under `cmd.Run`.
- `internal/proctree/proctree_other.go` (new, `!windows`): attach returns `0, nil`; Run is Start then Wait.
- Tests: `proctree_order_test.go` (portable), `proctree_unix_test.go`, `proctree_windows_test.go`, and `internal/eval/process_exited_parent_windows_test.go`.
- Callers: `internal/eval/process.go` `err := proctree.Run(cmd)`; `internal/routine/execute.go` default `runCommand = proctree.Run`. taskkill Cancel stays; `cleanupProcess` stays and is a no-op once Wait has returned.

Known gaps, stated and not claimed away:

- The job is assigned after CreateProcess returns, so a descendant the child starts before the assignment is outside the job. Go's os/exec cannot start a process suspended and resume it, and no undocumented resume call is added. The two Windows helper parents wait 500 ms before starting their leaf so the tests are about the exited-parent case and not about this gap.
- Nested jobs need Windows 8 or later. On an older host, or when assignment fails for any reason, the command runs as today (taskkill Cancel, `cleanupProcess`) and the failure is not an error of the run. It is also not reported anywhere.
- Unix ends the command's process group, so a descendant that left the group (setsid) lives on; a job object also ends that one, because no breakaway flag is set. No breakaway flag was added.
- Routine's default `runCommand` is covered by the compile and by the same `proctree.Run` in the eval test; routine tests inject their own `runCommand`, and no Windows test of routine's default was added, because the brief names one test through the real caller (eval).
