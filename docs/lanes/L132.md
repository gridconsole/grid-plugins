# L132 — Routine limits belong in workflows.md

Base: plugin main `0621ff66b3ec7a92a79b131db40a1bd4860beb03`, including L120
and L128. Branch: `lane-L132`. Regression commit: `d4ae07c`.
Implementation and README: `b1f5979`.

## Policy and diagnostics

Routine defaults now come from front matter in workspace `workflows.md` and
`projects/<name>/workflows.md`. Each key resolves independently: routine entry,
project, workspace, built-in default. Home routines use entry, workspace,
default. Every inherited source is validated before overrides; an invalid
masked value still refuses execution. Files with no front matter and empty
front matter supply no overrides, preserving existing template-only files.

The brief's explicit precedence differs from L128's implementation and report:
L128 did not inherit workspace defaults into projects. This lane follows the
requested entry > project > workspace > default order. Routine entry storage
remains scoped exactly as before; only policy inheritance changes.

`WorkflowPolicyError` retains the source level through list and CLI formatting.
For example, a bad workspace budget reports
`grid: workspace workflows.md: invalid routine_budget` with exit 2, without a
routine name, supplied value, or filesystem path. Project policy uses the
`project` label. Read and syntax errors also name the policy level and return
exit 2. Entry errors keep L120/L128 behavior. Validation still precedes execution,
interval skipping, and changes to run state.

Neither root/project `workflow.md` nor task-local `workflow.md` supplies limits.
On `grid routine run`, a legacy root or selected-project file with `routine_*`
front matter keys produces one stderr warning per file, naming the relative
source and its plural destination. Multiple keys do not duplicate warnings;
JSON stdout stays separate. Detection uses bounded, symlink-refusing reads and
the existing strict YAML reader. Unreadable or malformed legacy documents are
ignored; they neither supply policy nor block runs. Task files and body text
are not searched for migration warnings.

## Scope and existing tests

The implementation reuses `mdfile.Split`, `mdfile.Load`, the typed limit nodes,
and `safefile.Read`. No exported reader in `internal/workflow` supplies the
required typed policy; its task-specific readers would lose types or target the
wrong file. No new YAML parser or workflow export was needed. Neither
`internal/workflow/parse.go` nor person files changed.

The small supporting changes in `internal/routine/store.go` preserve policy
errors before list attaches routine names. `internal/cli/routine.go` prints
migration warnings and formats inherited errors before unwrapping limit errors.
The README's L128 paragraph now describes plural files and the requested
precedence. The contract README has no L128 routine-policy paragraph to move.
No existing endpoint, JSON field, source of routine entries, or timer definition
was removed or replaced; the module and generated artifacts are unchanged.

L120 tests are unchanged. Existing L128 tests changed in two files:

- `internal/routine/guard_limits_test.go`: `writeRoutineWorkflow` writes
  `workflows.md`, moving the existing timer guard regressions to the new source.
- `internal/routine/workflow_test.go`: snapshot and unsafe-file paths use
  `workflows.md`. Two expectations necessarily change beyond the filename:
  the snapshot test now expects workspace inheritance into its project, and
  the unsafe-file test expects the workspace diagnostic prefix. These follow
  the explicit precedence and source-label requirements above. Invalid-policy,
  snapshot, persistence, and fingerprint assertions remain in place.

`grid workflow show --policy` does not exist on this base. No policy-listing keys
or CLI flags were added; exposing routine keys in a future policy listing is a
follow-up.

## Regression evidence

Before implementation, the following new tests ran against the base code:

```text
go test ./internal/routine ./internal/cli -run 'TestRoutine(WorkflowsPrecedence|WorkflowBadLimitNamesLevel|OldWorkflowIgnoredAndWarned)$' -count=1
```

Workspace, project, and mixed-key precedence rows failed because plural-file
values were ignored. All six level/key diagnostic cases failed to return the
expected level-specific exit-2 refusal. Both legacy-location cases failed
because the old timeout still refused the run instead of being ignored and
warned. Default and explicit-entry rows passed as compatibility controls.

All these tests pass after implementation. Additional coverage accepts existing
files without front matter and rejects warnings for task policy or body text.
The old-location CLI test uses a future `last_run` and `--due` to skip execution;
invalid-policy tests use a nonexistent grid binary as an execution tripwire.
Inherited overrides remain absent from stored routine entries, and the existing
timer approval and executor snapshot tests pass on the new location.
